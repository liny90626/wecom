# OpenClaw WeCom 插件 v2.5.110-146 变更简报

## 2026-07-25（v2.5.110-146）

### 审查范围

本版本以 `released/2.5.110-118` 的简单、低等待路径为稳定性参照，分两轮完成：先对 Bot WS 入站合并、OpenClaw 会话接管、回复终态和热重载属主生命周期做两路 xhigh 对抗审查（第一轮），再针对“首反馈延迟、消息静默丢失、提示与事实不符”做一轮对抗式复核（第二轮）。目标是保留 v136-v145 已验证的完整回复能力，同时把首反馈延迟和消息丢失降到 v118 水平。

**验证环境变更**：开发依赖由 `2026.6.11` 升级至生产同版本 `2026.7.1`，7.1 独有路径（终态提交后 `freezeAbort` 冻结中止、`abortAndDrainAgentHarnessRun` 拒绝中止）首次在真实版本上完成类型检查与全量回归；`peerDependencies` 仍保留 `^2026.6.11`，代码继续双版本兼容。

### 第一轮：入站合并、接管顺序与属主生命周期

1. **文件后紧跟文字仍可能丢失文字或重复执行文件。** Bot WS 只短暂缓存媒体帧，普通文字也曾被固定等待；合并事件又只使用文字 `messageId` 去重，企微重投原媒体帧时可能在窗口结束后再次独立进入 OpenClaw。群聊合并键缺少发送者也可能把不同成员的相邻消息拼在一起。
2. **新消息会在确认可接管前提前终止旧任务。** pending 会话准备和 active OpenClaw dispatch 共用同一接管注册时序；若旧 run 正处于不可中断的 final/ACK 阶段，新消息先 supersede 旧 handle、随后自身又因 busy 被拒绝，可能造成新旧两条消息都没有最终结果。
3. **热重载后的旧回复可能继续借用新连接。** ReplyHandle 的 prepare、placeholder、preview、final retry 与真实 core Promise 没有统一绑定 WS runtime owner。
4. **busy 重试范围过宽。** 共享 busy helper 同时覆盖 flagless zero-output 和 `noVisibleReplyFallbackEligible`，后者可能代表回合已经执行或转入 deferred continuation。
5. **第二次 busy 提示投递失败缺少兜底。** dispatcher 直接发送第二轮提示，绕过 orchestrator 既有的 `deliver -> fail` 路径。

修复：普通文字立即派发，仅“媒体在前、文字在后”保留 `1s` 合并窗口；合并事件通过 `dedupeAliases` 同时去重媒体与文字，群聊键加入 `senderId`；pending 与 active 分层注册；ReplyHandle 绑定创建它的 runtime owner，stop/reload 撤销本地等待并跟踪真实 core Promise；只有“零输出、无 reasoning/tool/progress、无 fallback/deferred 标记且仍存在 active run”的明确未接收结果允许一次 `500ms` 重试；第二轮统一由 orchestrator 发送提示并复用失败兜底。

### 第二轮：相对 v118 的响应速度与消息完整性回归

1. **首反馈被整段准备工作挡住。** v146 候选把 `activate`（含占位气泡）推迟到 session prepare、预派发排空和接管排空之后。文件消息因此在**下载解密全程无任何气泡**，冷会话再加最多 `1s`，接管场景再加最多 `1s+5s`；v118/v145 是收到帧即发占位。
2. **prepare 期间被接管的消息整条丢失。** pending 层接管会直接中止尚未进入 OpenClaw 的旧消息，其正文与附件随之消失，用户却收到“已收到新消息，合并思考。✅”。典型场景：先发文件、约 2 秒后再发提问，文件下载尚未结束即被顶掉，Agent 完全看不到该文件。v118 两条消息都会进入 OpenClaw。
3. **被 OpenClaw 并入的消息被告知“未执行”。** 核心在 `runReplyAgent` 中把繁忙会话的新消息 steer/入队后提前返回，dispatch 结果为零计数且带 `noVisibleReplyFallbackEligible`；候选版对该结果回复“确认新指令未执行后再重试”，用户重发会造成重复执行。
4. **空 final 会清空气泡。** 企微流式帧携带整条气泡内容，`finish=true` 且 `content=""` 会把用户正在阅读的进度（如 Fast auto-off 提示）覆盖成空白。
5. **7.1 拒绝中止时新消息被直接拒收。** 7.1 在 `runAgentTurnWithFallback` 终态提交时调用 `replyOperation.freezeAbort()`，此后 `isEmbeddedRunHandleAbortable` 恒为 false，`abortAndDrainAgentHarnessRun` 返回 `aborted:false, drained:false`。这正是健康长任务投递答案的窗口，候选版在此直接拒收新消息并要求用户重发。
6. **合并窗口期间文件消息仍然静默。** 媒体帧在 `1s` 合并窗口内不派发，也就没有占位气泡。

修复：

- **即时确认与接管分离**：ReplyHandle 新增 `startPlaceholder`，只负责开占位气泡；`activate` 仍在确认接管后执行，继续负责认领 peer 与作废上一代 pending final retry。dispatcher 在入站被接受时立即 `startPlaceholder`，媒体帧在进入合并窗口前也先确认。
- **合并窗口复用同一气泡**：媒体+文字合并后的回合直接在媒体帧已开的气泡上作答，文字帧的 handle 从未开流，不会留下孤儿气泡。
- **被接管的 pending 消息并入后继消息**：正文按时间顺序拼接、附件以最新优先合并，`dedupeAliases` 与原有去重不变。内容合并严格限定**同一发送者**且双方均为普通消息类型；不可合并时（群内其他成员、event/welcome 回合）改为提示“本条尚未开始处理，如仍需要请重新发送”。已被 busy 拒绝的消息在提示前摘除，不会事后被并入执行。
- **提示与事实对齐**：`noVisibleReplyFallbackEligible` + 仍有 active run 判定为“已并入当前任务”，恢复 `dispatch-absorbed-by-active-run` 日志；“确认新指令未执行后再重试”只保留给核心确实拒绝（flagless zero-output，入站已 release）与预派发拒收两条路径。
- **空 final 以最后可见内容收口**，不再清空气泡。
- **不可中止时有界等待**：预派发排空在 `aborted=false && drained=false` 时增加最长 `3s`（`150ms` 轮询）的释放等待，仍在既有 `5s` handoff 屏障内；等待期间占位气泡已经在显示。只有超时仍未释放才拒收。

### 已知边界

- 媒体在前时仍保留 `1s` 合并窗口（占位气泡已提前显示，不再是静默等待）；文字晚于窗口到达会被 pending 接管逻辑并入后继消息。
- 群聊中不同成员的消息不会合并内容，被顶掉的一方会收到“尚未开始处理”提示，需要重新发送。
- 单条回合只有第一个附件会成为 `MediaPath`；文件+文件的合并保留最新文件。
- 预派发释放等待最长 `3s`；旧任务超过该窗口仍未释放时仍会拒收新指令并提示重发。
