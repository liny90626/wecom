# OpenClaw WeCom 插件 v2.5.110-147 变更简报

## 2026-07-29（v2.5.110-147）

### 审查范围

本版本针对现网使用 v146 后反馈的三类问题：①「⚠️ Something went wrong while processing your request.」莫名出现且频率明显升高；②长任务只回 `LLM request timed out.`，过程中没有任何思考块或中间答复；③思考块经常不出现，并偶发「发出去没回复、再发一条才显示」。三条都没有稳定复现步骤，因此先做机制分析再建复现环境。

### 复现环境（本轮的关键）

以往的 Bot WS 单测把企微 SDK 当成「秒回执」的 mock，因此**从未触发过投递层的真实约束**。本轮新增 `src/test-utils/wecom-gateway-sim.ts`，忠实建模 `@wecom/aibot-node-sdk@1.0.7` 的投递层：

- 每个 `req_id` 一条 FIFO 队列，同一时刻只允许一帧等待回执；
- 回执超时 `5000ms` 后丢弃该帧并继续下一帧；
- **回执只按 `req_id` 匹配**，某帧超时后它迟到的回执会 resolve 下一帧的 Promise；
- `replyStreamNonBlocking(finish=false)` 在有待回执时返回 `"skipped"`；

再叠加企微客户端「一帧流式内容整条覆盖气泡」的渲染规则，并记录气泡的每一次修订。加上这两件事之后，三条反馈全部稳定复现。

### 问题与修复

1. **一次丢失的回执让整轮进度永久失声**（对应 ②③）。`isTerminalReplyError` 把「回执超时」与「流已死」当作同一件事，任意一帧 5 秒未回执就永久熄灭进度通道：后续所有思考块与块预览被丢弃，用户盯着「⏳ 正在思考中…」直到任务结束，答案再以另一条新消息推来。长任务每几秒发一帧，命中概率很高——这正是「机率性」的来源。
   → 拆分为两个 latch。只有 `846605`（未知 req_id）/`846608`（流窗口过期）才退休进度通道；**回执缺失只标记该 `req_id` 的回执账本不可信**（`streamAckUnreliable`），进度继续绘制，而必须证明送达的动作（final、收流、接管提示）照旧改走主动推送。**持续型**失败（整个宽限窗口都有帧待回执）仍然退休通道并转后台通知。
2. **错误 final 抹掉用户正在看的过程**（对应 ②）。企微流式帧整条覆盖气泡，`LLM request timed out.` 一到，`<think>` 块连同全部进度瞬间消失。用户反馈的「怀疑 openclaw 的回复被 wecom 这边截断或去掉了」属实。
   → 错误 final 现在把思考块一并带上。思考块只占用该帧**剩余**的字节预算，不改变答案自身的分段限额（否则续文会被切成更多条主动推送消息）。
3. **被接管回合的核心失败文案被当成新消息推给用户**（对应 ①）。会话交接本身就是终结旧 run 的原因，旧 run 的失败文案对用户没有价值，却以主动推送落在新答案旁边。
   → 被接管且**纯失败文案**的 final 静默丢弃；被接管回合的真实答案、以及带媒体的 final 仍走原有接管路径（上传文件并说明原因）。
4. **v146 把接管公告推迟到排空之后，留下「已杀掉的 run 仍在线」的窗口**（对应 ①频率升高的直接原因）。v146 之前 `registerActiveBotWsReplyHandle`（即通知上一轮被接管 → 中止其 replyOperation）发生在预派发排空**之前**，v146 移到了**之后**，于是从「在 harness 层杀掉旧 run」到「告诉旧 dispatch 它被接管」之间出现最长 settle + 释放等待的空窗。OpenClaw 只有在 replyOperation 已被中止时才把 harness abort 判为静默的 user abort，空窗期内被杀掉的 run 会把自己算作失败并把文案投出来。
   → 改用同步的 `abortAgentHarnessRun` 取回「中止是否被接受」，**接受的同一 tick 内发布接管**；被拒绝（7.1 冻结中止＝健康 run 正在提交答案）则完全不碰旧回合，保留原有有界释放等待与拒收路径。释放等待轮询由 `150ms` 降到 `50ms`（纯交接延迟）。

### 代码走查追加修复

一轮独立 code review 后再修三处：

- **思考块前缀曾挤占答案的分段预算**：`resolveThinkingAwareBodyLimits` 是预览通道的辅助函数，从 3500 字符上限里扣前缀，且这套缩小后的限额被一路传进续文推送。3000 字符思考块 + 4500 字符错误 final 会从 2 条推送变成 5 条（每条间隔 800ms）。已改为思考块只吃该帧剩余字节，答案分段完全不受影响。
- **只丢回执的流再也走不到 9 分钟后台通知**：原本由「通道退休」分支挂载该通知，新分支没有挂载，而「持续型」截止分支对纯回执超时不可达（SDK 会在自己的 5 秒超时时出队，`hasPendingReplyAck` 早已变 false）。网关一旦停止回执，长任务将全程静默。已改为回执 latch 触发时即挂载通知，**预览一旦确认送达就撤销**，因此单次抖动不会打扰用户。
- **被接管失败文案的抑制过宽**：会连同该 final 携带的媒体一起吞掉。已限定为纯失败文案。

### 已知边界

- 一旦本轮出现过回执缺失，final 就固定改走主动推送：答案以新消息到达，进度气泡停在最后一帧且不再收口。这是「宁可多一条消息，也不能静默丢答案」的既有取舍。
- 被接管回合的失败文案不再送达；用户仍能从旧气泡上的「已收到新消息，合并思考。✅」或冻结的进度看出该回合已被合并。
- 若一轮内一次预览都没成功过、且流在 120 秒内就死，占位保活会结算流并连带取消后台通知；此时答案仍以主动推送到达。
- 真机（企业微信网关）体验仍未验证，需在发布后重点体验长任务过程信息、失败长任务的气泡内容、回复途中插入新消息三条链路。
