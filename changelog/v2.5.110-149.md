# OpenClaw WeCom 插件 v2.5.110-149 变更简报

## 2026-07-31（v2.5.110-149）

## 审查范围

本轮处理三件现网反馈，全部按「先复现、再定位、修复后验证」推进：

1. 同时/短时间内发送**文件 + 文字**，Agent 只响应其中一条；
2. 长任务运行中 OpenClaw **确有产出**，但插件只发「正在专注任务中…」的纯提示，产出被丢弃；
3. OpenClaw 衍生子任务时，子任务返回会推到企微 —— 需要判断是否正常、与插件是否有关。

## 一、文件 + 文字：两个方向都会丢一半

适配器只为**媒体**帧保留 1 秒合并窗口（`MEDIA_FIRST_TEXT_MERGE_WINDOW_MS`），文字帧立即派发。因此两种顺序各自失败，且失败方式不同：

- **先打字、后附文件**：文字回合已经在跑，文件作为独立入站进来，而文字的 pending 记录早在 `activate` 前被删除 ⇒ 无法并入；文件的预派发守卫再把文字的 run 杀掉，最终**只带文件**进 OpenClaw。复现后 `ctx.Body === "[file] report.pdf"`，指令彻底消失。
- **先附件、后打字**：裸文件会让 Agent 很快给出可见回复（「收到一个 PDF，需要我做什么？」）。等用户打完字，那个回合已经有可见输出 ⇒ 并入被整体挡掉，指令带着**零附件**进 OpenClaw。（附件下载会拉长 pending 窗口，反而让这条路径**偶尔**是好的——这正是它表现为「时好时坏」的原因。）

修复：pending 记录**保留到该次 dispatch 结算**（原来在核心派发前删除），后继消息因此可以并入一个「它即将杀死」的回合。三条边界：

- 已进入 OpenClaw 的前驱**不在注册时 supersede**——只有被接受的中止才能认领 peer，否则 busy 拒绝路径会丢掉它正在提交的答案（禁改 9）；
- **附件永远随行**：它是新指令需要的**输入**，不是用户已看到的产出；媒体事件自身的正文只是 `[file] <url>` 标签，丢掉不损失信息；
- **前驱正文**只在用户尚未看到该回合任何可见输出（`hasVisibleReplyBody` 或 final）时随行，避免重跑用户正在读的回复。

四种时序现在都成立：帧级 1 秒合并 / 下载期间并入 / 文件回合已开口 / 文字回合在跑。

## 二、长任务的产出被后台提示丢弃

流窗口关闭后气泡无法再刷新，但 Agent 仍在产出；9 分钟后的循环推送只带状态行，于是这段产出直到 final 才出现（现网案例：两条纯提示气泡覆盖了整整一分钟的真实输出）。

修复：后台推送先带上**用户尚未看到的可见正文**，再接状态行；**只有推送成功后**才推进已投递书签（`recordDeliveredBodySource`）——final 用同一份书签算续文，因此既不重复也不丢失。推理不参与（只在折叠 `<think>` 块内展示），`visibleReplyStarted` 也刻意不置位，保证之后被接管时剩余答案仍会推送。

## 三、子任务返回推到企微：机制正常，但插件侧被牵连出一个真问题

**结论：推送本身是 OpenClaw 的既定设计，不是插件行为。** `sessions_spawn` 默认 `mode:"run"`（结果作为工具返回值回到父 agent）；真正到达企微的是**完成通知**：子任务跑完后 OpenClaw 把结果作为提示投给**父会话**，`expectsCompletionMessage` 默认 `true` 时走 direct 优先——父会话还在跑就 steer 进当前回合，已空闲则新起一个父回合并把它的答复投递到渠道。所以推出来的是**父 agent 的答复**，不是子任务原始输出。要改是 OpenClaw 侧的旋钮（`mode`、`expectsCompletionMessage`、`subagent_delivery_target` hook）；插件拿到的 sessionKey 是父会话的，无法也不应区分。

**但插件侧确有一个被牵连出的缺陷。** 插件 outbound 在每次主动推送后调用 `markExternalActivity()`，它原本会：

```
stopPreviewFreezeTimeout(); stopPreviewStatusInterval(); cancelPreviewExpiredNotice();
```

`cancelPreviewExpiredNotice` 是**永久闩锁**。于是长任务运行途中只要发生过**一次**主动推送（子任务完成通知就是最常见来源），这个回合剩余时间就**再也不会有任何进度反馈**——气泡状态不再刷新，后台通知彻底关闭，一路静默到 final。它不需要丢 ACK，也不需要流窗口过期，是一条独立的静默成因。

修复：改为**顺延一个间隔**而非退休——重置状态计时、按重复间隔重新挂载通知。只有**已经启动过**的循环才可顺延，因此外部活动永远不会为一条健康的流凭空挂上通知；推送在途时也不会重复挂载（`schedulePreviewExpiredNotice` 在途期间自身会 bail，其 `finally` 只补挂一次）。

## 已知边界

- 群聊中「他人消息接管了正在运行的回合」时，旧回合收到的仍是「已收到新消息，合并思考。✅」，但跨成员并不合并内容——文案不够准确（既有问题，需要第三种提示语才能修）。
- 流仍然健康、但预览已冻结（>5 分钟或 >3000 字）时，冻结点之后的新正文仍要等到 final：后台推送只在通道退休/回执不可信时才启动。
- 子任务完成通知本身推到企微是 OpenClaw 的设计，插件不做过滤；要关闭需在 OpenClaw 侧调整。
- 一旦本轮出现过回执缺失，final 仍固定改走主动推送（v147 的取舍）。
