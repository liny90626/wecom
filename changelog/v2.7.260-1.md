# v2.7.260-1（2026-08-01，LinKy fork 维护版）

发布标签 `released/2.7.260-1`。本版做了三件事：根治「长任务全程无提示、最后只回一行英文错误」、把交付链上一处会**静默销毁完整答案**的丢弃点堵死，以及合并上游 `YanHaidao/wecom` 的新提交。

> **版本号说明**：规则仍是 `<上游基线>-<构建号>`。本版合并了上游的 `2.7.260`，基线随之变更，构建号按规则从 `1` 重新计数（上一版是 `2.5.110-149`）。

---

## 一、长任务全程静默 → 反馈改为时间驱动

**现网案例**：安排一个长任务后只收到两个气泡——气泡 1「正在思考...」，气泡 2「⚠️ 本次任务未完成（已运行 10m08s）：LLM request timed out.」中间十分钟没有任何提示。

**根因**：插件这一侧的三条反馈通道**全部是内容驱动**的——要先收到 OpenClaw 的产出才会更新气泡。而 OpenClaw 的 `reasoningMode` 默认是 `off`，一个纯工具执行的回合**不会产生任何流式回调**。于是三条通道同时静默，气泡停在最初的占位文案上，直到失败降临。此前的占位保活还有 120 秒上限（`MAX_KEEPALIVE_MS`），过后连那句静态占位都不再重发。

**修复**（净减法，不是加保护）：

- 删除 `MAX_KEEPALIVE_MS` 上限、推理流的定时器重置逻辑，以及独立的 `placeholderTimeout`；
- `setInterval` 换成**自重排的 `setTimeout`**，让节奏可以随回合变老而放慢；
- 满 30 秒即认定这是长任务，气泡从静态占位切换为**带耗时的专注提示**，并降到冻结状态的低频节奏。

净效果是**帧数下降**：10 分钟共 33 帧，而旧实现光前 2 分钟就发 40 帧。心跳在 `lastPreviewText` 出现后立即让位，绝不覆盖真实产出。

配套：气泡不可再重绘（企微流窗口约 6 分钟后返回 846608）时，不再 `settleStream()` 整个 handle——那会连带取消延后的后台推送，让静默的长任务继续静默；改为只退休气泡这条通道并移交给推送通道。`markExternalActivity` 里那处永久退休心跳的调用也改为**顺延重排**，与 v149 给另一条通道定的规则对齐。

## 二、漏消息：一处会静默销毁完整答案的取消逻辑

**要求**：所有 OpenClaw 侧过来的真实消息都不得遗漏。

对 `deliver()` 全链路逐条枚举丢弃点后，只有一处是真实损失：

```
shouldCancelForNewActivation: () => !supersededByNewInbound || (visibleReplyStarted && delivered > 0)
```

`!supersededByNewInbound` 对**任何一个正常结束的回合都为真**。于是这个序列会丢消息：回合 A 答完 → final 推送失败（用户一个字都没收到）→ 重试排在 20 秒后 → 用户在这 20 秒内发了下一条 → **A 的完整答案被永久销毁**。它**不需要接管、不需要 abort**，这正是它躲过前几轮排查的原因。

判据改为「**本次推送已有分片确认送达**」——只有在重推会造成重复时才取消：

```
shouldCancelForNewActivation: () => (finalPushProgress?.delivered ?? 0) > 0
```

代价是一条未送达的旧答案可能在新回复之后才落地（顺序颠倒），这与既有取舍一致：有界重复可以接受，静默丢失不可以。

另有一处**尚未证实**的丢弃：同一 handle 上出现第二条内容不同的 final 会被去重逻辑静默吃掉（去重本是为同一答案的重试设计的）。企微上没观察到实例，本版加了 `[wecom-b3] final-skip second-distinct` 警告日志，出现即可证实。

## 三、合并上游

上游 4 个提交全部只动 `package.json`。冲突逐条处置，**没有机械接受任何一边**：

| 字段 | 上游 | 处置 | 原因 |
| --- | --- | --- | --- |
| `version` | `2.7.260` | `2.7.260-1` | 基线跟上游走，构建号从 1 重新计数 |
| `peerDependencies.openclaw` | `^2026.7.0` | 保留 `^2026.6.11` | 已覆盖 2026.7.x，是上游区间的**超集**；跟过去会把 6.11 用户挡在门外 |
| `devDependencies.openclaw` | `^2026.7.0` | 保留 `^2026.7.1` | 自测须与生产同版本 |
| `@types/node` | `^22.22.0` | `^22.20.1` | 见下 |
| 三个运行时依赖 | 插入号区间 | 保留精确钉版 | `reply.ts` 建模的是 SDK **1.0.7** 的传输语义，版本漂移模型即失效 |
| `scripts.prepack` | 无清 `dist` | 保留清 `dist` | 防止陈旧产物混进包 |

**顺带修正上游一处缺陷**：`@types/node@^22.22.0` **在 registry 上并不存在**（22 线最高 `22.20.1`），任何干净的 `npm install` 都会 404 失败。但上游的意图是对的——`^25` 的类型领先于实际的 Node 24 运行时，是唯一「编译通过、运行时才崩」的危险方向。故取其意图、改其值为 `^22.20.1`。

## 边界说明

`LLM request timed out.` / `LLM request failed.` 本身源自模型网关，OpenClaw 会统一隐去原始错误文本；插件侧能做的是不再静默、不再丢答案，并带上耗时与框架。现网案例的 10m08s ≈ 608s 提示可能是 600s 代理超时——要坐实需把插件的 `[wecom-reply] error-final` 日志与 OpenClaw 的 `embedded run agent end … rawError=` 对一次时间戳。
