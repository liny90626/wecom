# v2.7.260-11（2026-08-15，LinKy fork 维护版）

发布标签 `released/2.7.260-11`。收口现网两条反馈：**思考块过长导致回复失败**、**长任务过程仍在丢失且收尾记录令人困惑**。顺带把消息上限从「盲目保守」调到官方额度的约 75%，并补上「思考结束、工具跑很久」时气泡假死的空档。

> **版本号说明**：规则不变，`<上游基线>-<构建号>`。上游基线仍是 `2.7.260`，构建号递增到 `11`。

## 一、思考块过长 → 气泡里只有思考块、没有答案

### 复现与证伪

先按反馈里的猜测（超过字数上限）验证：把长 reasoning 流、9k 字面 think 块 final、错误 final、长正文四种形态逐帧量过，**所有帧都在 3500 字符 / 12000 字节内**，也远低于官方 20480 字节上限——**不是尺寸问题**。第二个假设（`mergeReplyText` 退化阻塞事件循环）也被实测证伪：单次最长阻塞 15ms，微基准 16k 段 120 次合并仅 9ms。

### 根因：思考块是唯一没做 wire 安全化的文本

正文走 `toWeComMarkdownV2`（跨行删标签、转码块、解实体）；思考块只做了 `/<[^>\n]*>/g`——**只删同一行内成对的 `<…>`**。于是模型推理里的裸 `<`（`if (a < b)`、`Map<string`、XML 片段）原样上线。而思考块结尾**一定有 `</think>`**，也就是说块内任何一个裸 `<` 后面必然能配到一个 `>`：客户端把 `< … </think>` 整段当成一个标签吃掉，**块永远不闭合，后面的答案跟着消失**。被截断的代码围栏（```）是同一种吞噬。推理越长，命中裸 `<` 或半截围栏的概率越高——这就是「只在思考块过长时发生」的由来。

### 修复

思考块改走正文同一条管线，再把残留 `<` 中性化为 `&lt;`（转义会膨胀，所以必须发生在预算之前，禁改 32 的顺序不变）。悬挂修复同时覆盖半截实体与代码围栏——归一化之后还活着的 ``` 按定义就是无配对的，直接全部移除，不再只从一侧配平。

```
模型原文 : 先判断 if (retries < maxRetries) 再决定是否重试。
修复前   : <think>先判断 if (retries < maxRetries) …</think>   ← </think> 被吞
修复后   : <think>先判断 if (retries &lt; maxRetries) …</think>
```

## 二、思考块输出到一定长度就再也收不到消息

### 复现

六次累计推理快照，**只发出 2 帧**。

### 根因：头部截断让帧不再变化

思考块按**头部**截断，累计推理一旦越过上限（3000 字符 / 8000 字节），每次渲染逐字节相同 → `previewText === lastPreviewText` 等值判定当成重复帧丢弃 → **整条预览通道静音**，气泡就停在那个长度不动，直到 8 分钟心跳或最终答案。

### 修复：显示最新的一段

改为**尾部窗口**：推理在动，帧就在动；尾部也是有用的那一半（模型此刻在想什么）。块内首行提示 `…（较早的思考已省略）`。两端都可能截断，因此代理对在**头尾都不得被劈开**（新增三种边界用例）。

### 顺带：思考块与正文共用同一帧预算

`resolveThinkingAwareBodyLimits` 从同一帧的 3500 字符 / 12000 字节里**先扣思考块**，3000 字符的思考块会把正文预览压到 **484 字符**（下限甚至 100）。现在正文在场时思考块收紧到 **800 字符 / 2400 字节**（与过程日志同一条规矩），正文可见量升到约 2680；纯思考气泡不受影响，仍拿满整帧。两半改由**一次 `resolveThinkingFrameLayout` 同时产出**——此前分两处计算，存在算不到一起去的结构性风险。

**提速**：节流判断挪到合成之前。推理是累计快照、每秒几十次，过去每次都要归一化整段再丢掉，占的正是流式回执等待的那条线程；渲染也只对能装下的窗口做，成本与推理总长解耦。

## 三、长任务：8 分钟后仍丢过程 + 收尾记录令人困惑

### 复现（15 分钟 / 22 步 / 6 分钟流窗，逐帧采样用户可见状态）

| 时间 | 修复前 | 修复后 |
| --- | --- | --- |
| 05:35–08:00 | **完全没有反馈** | 06:22 起就有推送 |
| 首条推送 | 把 1–10 步**全量重发**（1–7 步刚在气泡看过） | 只送第 8 步 |
| 中段 | 每分钟一条 | 有新步骤才推，最短 60 秒 |
| 收尾 | 答案 + 「📋 共 22 步」**却只列 2 步** | 只有答案 |

### 三处根因与修复

1. **6→8 分钟盲区是自造的**：企微流窗约 6 分钟死亡，而推送闸门写的是「回合满 8 分钟」。现在**流窗一死推送立刻接手**（并有 5 分钟下限，防止早期异常拒绝把年轻回合变成推送会话）；纯状态推送仍守 8 分钟绝对门槛。
2. **首推重复**：被企微拒绝（846605/846608）的那一帧**再也没人能覆盖它，final 也不行**——那一刻它已经是永久聊天记录。于是把它已确认的步骤前缀**并入同一个 durable 书签**（不是第二个书签）。两个反例在走查中补上：一帧**不含日志**的正文预览/冻结状态会整条覆盖气泡，那份「已展示」必须立即作废；被 wire 合成器裁掉尾部的视图**一律不认账**。
3. **记录推送取消**：长任务的过程本来就随进行中的推送逐条落在聊天记录里，收尾只发答案。`maybeFlushProcessRecordPush` 及其常量整体删除。
4. **推送节奏**：有新内容按 60 秒网格推；**无新内容的状态推送要先静默 5 分钟**——它的职责是证明静默回合还活着（禁改 25），不是每分钟打点。

## 四、消息上限：从「盲目保守」调到官方额度的约 75%

官方文档明确 stream `content` 上限 **20480 字节**。而 `12000` 的来历是 `v2.5.110-112` 的一句「保持…为 12,000 bytes，**避免盲目放宽限制引入客户端截断**」——**不知道官方数字时的保守猜测**，仓库里没有任何一次实测记录支撑它。

| 常量 | 原值 | 新值 | 占 20480B |
| --- | --- | --- | --- |
| `WECOM_STREAM_FINAL_MAX_CHARS`（答案每段） | 2000 | **5000** | 中文 15000B ≈ 73% |
| `WECOM_STREAM_MAX_BYTES`（帧字节） | 12000 | **15360** | 75% |
| `WECOM_STREAM_MAX_CHARS`（预览帧） | 3500 | 不动 | — |
| `BLOCK_PREVIEW_MAX_CHARS`（冻结阈值） | 3000 | 不动 | — |

实测（仓库自己的分段器）：**6000 字答案 4 条 → 2 条**，10000 字 6 条 → 3 条，20000 字 11 条 → 6 条。后两个常量刻意不动——放大它们会加重回执槽压力，而回执槽是这套传输真正的脆弱点。

## 五、思考结束、工具跑很久：气泡假死

`scheduleHeartbeat` 把下一次心跳**直接排到第 8 分钟**，`sendPlaceholder` 又在有预览时提前返回——这段静止是**代码层面安排好的**，不是偶然。

**可见性与「长任务」是两个问题，现在两个触发器**：

- 「长任务处理中，**请勿打断**」要求用户改变行为，仍守 **8 分钟绝对门槛**。
- 「还活着」由**沉默时长**驱动：一旦运行侧报告工具活动（`onToolStart`，本就订阅、仍不产生任何可见文字，禁改 35 不破），气泡静默满 **90 秒**就重绘完整帧（思考块＋正文＋过程日志＋计时），8 分钟前用更轻的 `【处理中，已用时X】`。真实产出会重置该时钟。
- **没有工具活动的回合完全维持现状**，v150 的零产出保底一步没动。

沉默时钟从「**任一通道最后一次上屏**」起算：心跳重绘不是已确认预览，只按确认预览计时会让截止点停在过去、定时器 0 延迟反复触发——敏感性验证把它抓成了 1002 帧空转。

## 边界说明

- **放大后的显示未经真机验证**：官方给的是 API 上限，不保证客户端不折叠/截断。建议发两条带尾部哨兵的消息定案——3500 字（10500B）与 6000 字（18000B），看尾部是否完整。这是本轮唯一没有证据覆盖的改动。
- **最后 ≤60 秒产生的步骤不再补发**：这是「取消独立记录推送」的直接代价，答案随即到达并取代它们。
- **纯静默长任务的兜底状态从每分钟变为每 5 分钟**：仍是时间驱动（禁改 25 不破），但「还活着」的信号变稀。
- **正文预览仍在 3000 字符处冻结**，冻结后的新正文要等 final 分段发送；沉默看门狗也不覆盖冻结态（那时气泡里已有满屏正文可读）。
- `Map<string, item>` 这类泛型在思考块里仍会被 `stripHtml` 吃成 `Map`——正文管线固有行为，本轮刻意未动共享适配器，以免污染验证信号。
- 上游 `YanHaidao/wecom` 的新提交本轮仍未合并；`npm audit --omit=dev` 仍报 `undici@7.28.0` 的 1 个 high 告警（修复版本 7.29.0），本轮未扩大依赖升级范围。
