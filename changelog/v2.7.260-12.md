# v2.7.260-12（2026-08-26，LinKy fork 维护版）

发布标签 `released/2.7.260-12`。本轮起因是一次**上游核查**：企微在 2026-08-10 ~ 08-17 重写了整套智能机器人协议文档，并首次发布了官方 OpenClaw 插件与 wecom-cli。把新文档、SDK 1.0.7 的**实际源码行为**与本插件逐条对照后，发现一个已复现的真实缺陷、一个高危依赖告警、一处与官方文档不一致的发送姿势。

## 一、被企微踢下线时，插件把断连通知当成一条用户消息去跑了一轮 agent

### 协议事实

企微规定**同一机器人同一时刻只能保持一条长连接**。新连接订阅成功后，服务端会向**旧连接**推送 `disconnected_event`，随后主动断开它（doc 62156，2026-08-13）。官方原文：「收到此事件后，开发者应停止使用当前连接」。

SDK 1.0.7 已经完整实现了这条语义——停心跳、清待发队列、`isManualClose = true`（**故意不重连**）、`ws.terminate()`。但它把这个事件和用户事件**放在同一条 `event` 通道**上发出。

### 两处独立的根因

1. **事件被当成了消息**：`sdk-adapter.ts` 的 `client.on("event", …)` 不区分事件类型，这一帧照走 `handleFrame → dispatchEvent`。`inbound.ts` 把它映射成 `inboundKind:"event"`、正文 `[event:disconnected_event]`；而该帧里**没有 `from.userid`、没有 `chattype`**，于是 peer 落成 `direct:unknown`。也就是在连接正在被终止的那一刻，插件启动了一轮完整的 OpenClaw 运行；等它产出答案，`reply.ts` 的 `else if (isEvent)` 分支还会朝 `unknown` 发一条 markdown。
2. **诊断从不触发**：判断「是否被踢」用的是关键词 `kick` / `owner` / `replaced`，来自 `2.3.9`（SDK 还没有这个事件的年代）。SDK 1.0.7 的真实 reason 是 `New connection established, server disconnected this connection`——**一个关键词都不含**，`ws-kicked` 因此永不落账，运维侧看不到真正的原因。

### 复现

先写用例、后改代码，两条断言在修复前立即变红：

```
输入：client.emit("event", <disconnected_event 帧>)
      client.emit("disconnected", "New connection established, server disconnected this connection")

handleEvent 调用次数   = 1                       ← 期望 0
派发出去的事件         = inboundKind:"event"
                        text:"[event:disconnected_event]"
                        peer:{peerKind:"direct", peerId:"unknown"}
operational issues     = []                      ← 期望 ["ws-kicked"]
```

### 修复

在 `handleFrame` 入口**精确匹配** `disconnected_event`：记一条 `ws-kicked` 后直接返回，不建 reply handle、不派发。只匹配这一个事件类型，不做白名单式收敛——`enter_chat` / `template_card_event` 的行为逐字节不变（现有用例全绿即判据）。

**刻意不重连**：现在这条连接的所有权已经属于新实例，重连会把它再踢掉，对方的框架又会重连回来——两个实例会无限互踢。官方插件在自己的实现里对同一场景写了同样的注释与同样的处理。运维可见性由 `ws-kicked` 诊断与 session `running:false` 承担。

**未处理 `feedback_event`**：本插件从不设置 `feedback.id`，按官方文档该事件不可能被触发。为不可能发生的场景加处理属于防御性膨胀，本轮不做。

## 二、`undici` 7.28.0 → 7.29.0

`npm audit --omit=dev` 此前报 `undici 7.0.0 - 7.28.0` 命中 5 条 advisory（含 **1 个 high**）：retry interceptor 导致下游响应错位、退化的私有缓存指令引发跨用户信息泄露与解析崩溃、blob body 的 `type` 属性 CRLF 注入、`Cache-Control` 等号旁空白导致的跨用户信息泄露、`setCookie` 未净化导致的 cookie 属性注入。

`src/http.ts` 直接使用 `ProxyAgent` + `fetch`，正是这些 advisory 的作用面。7.29.0 是官方修复版本，7.x 内的 minor，**产线代码零改动**。升级后 `npm audit --omit=dev` 输出 `found 0 vulnerabilities`。

## 三、主动推送显式带上 `chat_type`

官方 `aibot_send_msg` 文档（doc 62158，2026-08-12）写明：`chat_type` 取 `1` 单聊 / `2` 群聊，**「0 或不填则自动兼容（优先按群聊处理，建议明确指定）」**。

本插件一直不填这个字段——也就是每条主动推送都让服务端**先按群聊猜一次**。而入站帧早就告诉了我们答案：`reply.ts` 里的 `peerKind` 正是从 `body.chattype` 推出来的，`peerId` 也据此在 `chatid` 与 `from.userid` 之间选择。既然我们手上的信息更准，就没有理由让服务端去猜。

SDK 1.0.7 本身没有这个字段，但不必等新版本：`sendMessage(chatid, body)` 内部是 `{ chatid, ...body }`，`sendReply` 又原样入帧，多带一个字段即可上线；类型 `SendMsgBody` 未声明该字段，因此**只在调用点断言**，不全局放宽类型。

**改动范围刻意受限**：

- `reply.ts` 里**所有**朝 `aibot_send_msg` 发的路径都带上，一共四处：走注册 push handle 的那条、handle 不可用时回落到 SDK client 的 `sendViaClient`、以及事件回复的正常与错误两条分支。这是被用例一步步逼出来的——端到端用例先抓到「只改了 push handle 那条」，全量套件又抓到事件回复分支仍在让服务端猜。**留一条路径猜测，就等于没修**。
- `outbound.ts` 的 Agent 主动发消息**不动**：那条路径只有一个 `to`，拿不到可靠的会话类型，猜不如不猜。handle 的新参数因此是**可选**的，省略时一个字段都不加、行为逐字节不变（`outbound.test.ts` 里 `toHaveBeenCalledWith("lisi", "hello ws")` 的精确实参断言就是这条边界的守卫）。
- 媒体推送路径同样未改，保持现状。

## 上游核查结论（本轮的另一半产出）

- **`@wecom/aibot-node-sdk` 没有新版本可升**：`1.0.7`（2026-05-12）仍是 latest，本仓库已锁 `1.0.7`。旁证：官方自家插件依赖 `^1.0.6`，解析结果同样是 1.0.7。
- **协议文档整套重写**（doc 62153–62160、62131/62132，2026-08-12 ~ 08-17），旧的「智能机器人长连接」（doc 60904）已被取代。逐条核对后，与本插件现状一致、无需改动的部分包括：stream `content` ≤ 20480 字节（本插件 15360 = 75%）、30 条/分钟与 1000 条/小时、`<think></think>` 官方渲染折叠、心跳 30 秒、欢迎语必须走 `aibot_respond_welcome_msg` 且 5 秒内（本插件用的正是 `replyWelcome`）、入站 `quote` / `mixed` 结构、临时素材的分片与体积限额。
- **官方首次发布了自己的 OpenClaw 插件**（`@wecom/wecom-openclaw-plugin@2026.8.17`）与 `@wecom/cli@1.1.0`，走的是 **CLI + Skills** 路线，与本 fork 的插件内置工具是两条不同技术路线。本轮只把它当作交叉验证的参照物（`disconnected_event` 的处理方式即由它印证），不评估路线切换。
- **`wecom_doc` 无需适配**：它覆盖的 wedoc 分组（管理文档 / 管理收集表 / 智能表格 / 在线表格）最近一次更新都在 2024-05-30 或更早；2026 年唯一的新增是「管理智能文档内容」16 个 smartpage 接口，属可选扩展。

## 边界说明

- **`chat_type` 未经真机验证**：本轮唯一改变上线帧形态的改动。建议各发一条单聊推送与群聊推送确认送达且不串会话；若异常，直接 revert 该 commit，不牵连其余两项。
- **`chattype` 缺失的假想帧**：若企微某天在群聊帧里不带 `chattype`，我们会填 `chat_type:1`。但同样的前提早就决定了 `peerId` 的取值，真出现这种帧，推送目标本来就已经错了——本轮没有新增暴露面。
- **被踢后不自动恢复**：这是期望行为。恢复手段是停掉重复实例后由 OpenClaw 重新拉起该频道。
- **`disconnected` 里的 `kick/owner/replaced` 关键词保留**：无法证明它对 WS close reason 也是死代码，本轮不动无关行为。
- **`wecom_mcp` 转下一轮专项**：官方 CLI 概述（doc 61944）给出了完整的 `biz_type` 取值表（`msg` / `mail` / `doc` / `todo` / `schedule` / `meeting` / `disk` / `contact` / `media`），与本插件 4 个既有经验值 4/4 吻合；而工具描述只提了其中 4 个，且表格 / 智能表格 / 智能文档共用 `biz_type: doc` 这一点从未写明。另有 `tools/list` 返回体无上限的问题待评估。已在 `goal.md` §8 立项。
- 上游 `YanHaidao/wecom` 的新提交本轮仍未合并。
