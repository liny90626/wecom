# v2.7.260-13（2026-08-26，LinKy fork 维护版）

发布标签 `released/2.7.260-13`。收口现网反馈：**同一个 docid、同一个目标文档，用 `wecom-cli` 读写都成功，改用 `wecom_mcp` 后返回 `851003 no authority`**；而且 MCP 此前一直正常，企微 2026-08 更新文档之后才出现。

> **版本号说明**：规则不变，`<上游基线>-<构建号>`。上游基线仍是 `2.7.260`，构建号递增到 `13`。

## 一、根因：`category` 被原样当成 `biz_type` 送给了企微

`wecom_mcp` 的 `category` 参数，一路直通到 `aibot_get_mcp_config` 的 `biz_type`——中间没有归一、没有校验：

```ts
biz_type: category,   // 模型给什么就发什么
```

而官方取值表（CLI 概述 doc 61944，2026-08-14）里，**取值与能力名并不同名**：

| 能力 | `biz_type` | 工具前缀 |
| --- | --- | --- |
| 消息 | **`msg`** | `message_*` |
| 邮件 | `mail` | `mail_*` |
| 文档 / 表格 / 智能表格 / 智能文档 | **`doc`（四者共用）** | `doc_*` / `sheet_*` / `smartsheet_*` / `smartpage_*` |
| 待办 | `todo` | `todo_*` |
| 日程 | **`schedule`** | `calendar_*` |
| 会议 | `meeting` | `meeting_*` |
| 微盘 | `disk` | `disk_*` |
| 通讯录 | `contact` | `contact_*` |
| 素材 | `media` | `media_*` |

也就是说，模型按能力名猜出来的 `smartsheet` / `smartpage` / `sheet` / `calendar` / `message` **都不在表里**。而**企微对认不出的 `biz_type` 不会报错**，只会给回一个没有作用域的 URL；配置被缓存下来之后，之后每一次调用都返回 `851003 no authority`——看起来像权限问题，实际是品类错了。

这同时解释了「以前正常」：`2026-08` 之前的取值集合更宽松，本次文档更新把表格 / 智能表格 / 智能文档合并进了 `doc`。也解释了「CLI 通」：`wecom-cli smartsheet …` 内部走的就是 `doc`。

> **诚实边界**：我手上没有现网日志，无法 100% 断定你那次调用用的是哪个 `category`。本轮修复对两种情况都成立——品类错了会被归一修好；真是服务端授权问题，则新增的日志与提示会在**下一次发生时一次性定性**（见第四节）。

## 二、修复（全部落在边界层，不动 JSON-RPC 与会话语义）

1. **归一**：别名表把 `smartsheet` / `smart_sheet` / `sheet` / `spreadsheet` / `smartpage` / `wedoc` / `calendar` / `message` / `email` / `drive` / `contacts`（以及「智能表格」「日程」等中文名）映射到官方 `biz_type`。
2. **认不出的取值原样放行**并打一条告警——**不写死枚举**。官方随时可能加新品类，写死会把插件锁在今天这张表上。
3. **缓存键改用归一后的 `bizType`**：`smartsheet` 与 `doc` 不再各持一份指向同一作用域的配置和会话。
4. **授权类业务错误自愈一次**：`850002` / `851003` 先作废这份配置、重取后再试，**只试一次**——真没授权时再试也只是把同一个错误走一遍。
5. **仍失败则给可执行提示**，而不是把一个裸错误码丢给模型：授权 7 天有效期需成员重新授权、智能表格记录写入在企业可见范围超过 10 人时被官方限制（应改走该表「接收外部数据」的 Webhook）、当前 `biz_type` 是否与目标资源匹配、官方取值有哪些。
6. **缺 `category` 时直接给出官方取值**，不去打企微。

## 三、举一反三修掉的三处

- **业务错误码此前完全静默**：`851003` 只是被原样返回给模型，日志里一个字都没有——这正是这次要靠猜的原因。现在业务错误码与 `biz_type` 一起落日志。（和 `-12` 的 `ws-kicked` 是同一类毛病：**故障发生时没有任何可查的痕迹**。）
- **配置 URL 带着授权凭证被完整打进日志**：现在日志只留 `origin + path`，query 与 fragment 一律不外发。
- **`tools/list` 返回体没有上限**：`doc` 一个品类就有 **60+ 个工具**（13+10+28+11），全量 `inputSchema` 会一次吃掉一大块上下文。现在超过 32KB 就退回「名称 + 说明」索引，并说明用 `method` 作前缀（如 `smartsheet_`）再取完整 schema；**小品类的输出逐字节不变**。旁证：官方插件自己也把这批参数说明拆成 `references/*.md` 按需读（smartsheet 一项 154KB）。

## 四、下次再出问题怎么一次定性

升级后 `[wecom-mcp]` 会打出：

```
config ready account=… bizType=doc url=https://…/stream/abc        ← 归一后的品类 + 脱敏 URL
biz error account=… bizType=doc method=smartsheet_records_add errcode=851003 errmsg=no authority
biz error persists account=… bizType=doc method=… errcode=851003    ← 重取配置后仍然失败
```

- 若 `bizType` **不是** `doc`（例如打出 `bizType=smartsheet`，说明命中了未知取值的放行分支）→ 品类问题。
- 若 `bizType=doc` 且出现 `biz error persists` → 服务端授权问题，按返回里的 `hint` 逐条排查。

## 边界说明

- **本轮没有真机验证**：修复依据是官方取值表与代码路径，不是现网复现。请在真机上按第四节看一眼日志确认。
- **未知 `biz_type` 仍然放行**：这是刻意的（不锁死未来品类），代价是拼错的品类不会被立刻拦下，只会告警。
- **`tools/list` 降级阈值 32KB 未经现网标定**：`doc` 品类的真实返回体积没有实测过。若真机上 `doc` 的完整清单其实不到 32KB，这段限幅就是一段永不触发的保险。
- **`protocolVersion: "2025-03-26"` 未动**：今天跑得通，没有任何证据支持升级。
- **HTTP 层 401/403 未加特殊处理**：没有证据表明企微会以此形态返回授权失效，按猜到的状态码写分支属于为不确定场景加防御。
