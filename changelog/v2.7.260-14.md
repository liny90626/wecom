# v2.7.260-14（2026-08-26，LinKy fork 维护版）

发布标签 `released/2.7.260-14`。本轮把 `wecom_mcp` **严格对齐官方实现**，并修掉 `-13` 没找到的真正根因。

> **版本号说明**：规则不变，`<上游基线>-<构建号>`。上游基线仍是 `2.7.260`，构建号递增到 `14`。

## 零、先更正两处判断

**① `-13` 的根因判断不完整。** `-13` 把现网的 `851003 no authority` 归因到「`category` 被原样当成 `biz_type`」。那是在没有官方源码时能做的最好推断，修复本身（缓存键、日志、限幅）仍然有价值，但**真正的根因是另一件事**（见第二节）。

**② 「企微废弃了 MCP 平面」这个结论是错的。** 事实是：最新的官方插件 `@wecom/wecom-openclaw-plugin@2026.8.17` 把 `wecom_mcp` **从自己的插件里**移除并迁到了 `wecom-cli`（包内留了一条迁移告警），但**企微的 MCP 能力面本身仍在维护**——官方文档里 MCP（101848）与 CLI（101847）是「AI 能力」下的**并列两块，均于 2026-08-12 更新**。把「插件的产品选择」推广成「平台的废弃」是我的错误，已收回。

## 一、找到了可参考的官方实现

`@wecom/wecom-openclaw-plugin@2026.7.2` 里保留着完整的 `src/mcp/`：

```
transport.js            549 行   ← 传输层
tool.js                 224 行   ← 工具定义（接口与我们完全一致）
interceptors/           6 个     ← biz-error / doc-auth-error / msg-media /
                                   smartpage-create / smartpage-export /
                                   smartsheet-upload
共 1814 行
```

`wecom_mcp` 本来就是官方插件的工具名，本 fork 与它同源。逐条对齐后发现：**SSE 解析、会话管理、缓存清理、`-32001/-32002/-32003` 错误码处理，我们与官方本就一致**（同源），真正的差异只有下面几项。

## 二、根因：每次请求都少了一个身份 header

官方在每一次 MCP HTTP 请求上都带：

```js
export const WECOM_USERID_HEADER = "x-openclaw-wecom-userid";
...
if (normalizedRequesterUserId) headers[WECOM_USERID_HEADER] = normalizedRequesterUserId;
```

**我们一次都没发过。** MCP 平面是**「代替成员」**操作的（官方文档原话：「各能力权限需成员单独授权」），不带这个 header，服务端就不知道该以谁的身份执行 —— 对成员作用域的资源自然返回 `no authority`。

这同时解释了现网的两个现象：

- **CLI 通**：`wecom-cli auth init` 绑定了具体成员，请求天然带身份。
- **以前正常**：企微这次更新开始校验请求身份。

> 这个 header **不在任何公开文档里**，只存在于官方插件源码中——所以不读官方源码就找不到它。

## 三、本次对齐的四项

1. **`x-openclaw-wecom-userid`**：握手（`initialize`）与每一次 `tools/list` / `tools/call` 都带上，取值保留**原始大小写**。
   为此给 `WecomSourceSnapshot` 新增 `requesterUserId` / `chatId` 两个**原文**字段——已有的 `peerId` 是被强制小写的查找键，不能当身份用。官方源码在同一处留了警告：小写之后 `aibot_send_biz_msg` 会报 `93006 invalid chatid`。
2. **官方 User-Agent**：`OpenClawPlugin/<version> <platform>/<arch>`，并改用 **undici 的 fetch**——官方注释写明这是为了绕开 Node 18.0–18.17 原生 fetch 无法自定义 UA 的 bug，而 undici 本就是本仓库的生产依赖。新增 `src/version.ts`，由 `version.test.ts` 与 `package.json` 对账，**发版漏改会直接变红**。
3. **清缓存的业务错误码改为官方集合 `{850001, 851014}`**（机器人授权过期 / 被重置）。我们原来的 `{850002}` 没有任何依据，大概率一直是错的。
4. **新增文档授权引导卡片**：`doc` 品类命中 `{851013, 851014, 851008}` 时，通过 `aibot_send_biz_msg`（`biz_type=1` 文档权限）让企微**直接给用户推一张授权卡片**，并把原始 `help_message` **拦下不喂给 LLM**——授权步骤由模型转述只会走样，用户要点的是卡片。拿不到会话上下文时不推卡片，但仍返回「去哪里重新授权」的提示。

## 四、撤回上一版我自造的两处

严格对齐官方，`-13` 里这两处已移除：

- **`biz_type` 别名归一**（`smartsheet`→`doc` 等）：官方是**原样透传** `category` 的。
- **`851003` 的重试与自拟提示文案**：官方对 `851003` 没有特殊处理。按官方 CLI 技能文档，`851003` 的常见成因是**企业可见范围超过 10 人导致智能表格写入受限**，官方给的解法是走该表「接收外部数据」的 Webhook，而不是重试。

## 五、保留的两处本地增强（刻意的偏离，都不改 MCP wire 行为）

- **配置 URL 在日志里脱敏**：官方 `getMcpUrl` 会把带授权凭证的完整 URL 打进日志，我们只留 `origin + path`。
- **`tools/list` 超 32KB 退回名称索引**：官方没有上限；`doc` 一个品类就有 60+ 工具，全量 `inputSchema` 会一次吃掉一大块上下文。小品类输出逐字节不变，降级时说明如何用 `method` 前缀取完整 schema。

## 边界说明

- **本轮仍未真机验证**：身份 header 是从官方源码读出来的，不是现网复现。请在真机上确认：① 之前 `851003` 的操作现在能通；② 日志里 `[wecom-mcp]` 不再出现 `biz error`。
- **`plugin_version` 未动**（仍是 `wecom-dual-plane`，官方发的是自己的版本号）：配置拉取本来就成功（拿得到 URL），说明企微不校验这个值；改它是无证据的 wire 变更。
- **官方另外 5 个拦截器未移植**：`msg-media`（`get_msg_media` base64 拦截）、`smartpage-create` / `smartpage-export`（本地文件读写）、`smartsheet-upload`（本地文件上传）。它们都涉及本地文件系统与沙箱边界，属于功能扩展，需要单独立项评估。
