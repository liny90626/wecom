> **验证版，尚未打 tag / 未推远端。** `2.7.260-14` 的冒烟测试失败后，本轮修掉两处**我自己在 -13/-14 引入或做错**的问题，等真机验证通过再发布。

## 零、冒烟测试结果与它排除掉的东西

`2.7.260-14` 装机后现网复测：

```
wecom_mcp(action=list,  category=doc)              → 成功，返回 19 个工具
wecom_mcp(action=call,  category=doc,
          method=sheet_get_info, <真实 docid>)     → 仍然 851003 no authority
wedoc CLI  sheet_info   <同一个 docid>              → 正常，返回 7 个页签及行列信息
```

这组对照排除了一大片可能性，也把范围缩到了一点上：

| 观察 | 排除掉的 | 剩下的 |
| --- | --- | --- |
| `tools/list` **成功** | 配置拉取、URL、会话握手、**品类级授权**都正常 | — |
| `category` 传的就是 `doc` | 「品类传错」（这也证明 `-13` 的别名归一根本不是解药，撤回是对的） | — |
| 同一 docid CLI **通**，MCP **不通** | 「文档本身没授权」 | **这份文档的访问权属于成员，而 MCP 调用没带成员身份** |

CLI 用的是 `auth init` 扫码绑定的那个成员的凭据，天然带成员身份；MCP 走的是机器人长连接换来的 URL，**成员身份要靠请求头透传**。品类授权给了机器人，文档访问权却属于成员——这正是 `list` 通而单文档不通的形态。

## 一、身份来源我取错了（`-14` 很可能根本没把 header 发出去）

官方 `index.js` 的 `registerTool`：

```js
const trustedRequesterUserId =
  ctx.messageChannel === CHANNEL_ID ? ctx.requesterSenderId?.trim() ?? undefined : undefined;
```

`ctx.requesterSenderId` 是 **OpenClaw core 提供**的字段，类型注释写明「Trusted sender id from inbound context (runtime-provided, not tool args)」，官方的变量名就叫 `trustedRequesterUserId`。

`-14` 里我没用它，而是绕道**自己的 `source-registry`** 去查——而工具注册的时机可能早于入站记录写入，那条路很可能一直是空的，等于 `x-openclaw-wecom-userid` **压根没发出去**。这也解释了为什么 `-14` 装上去毫无变化。

**修复**：优先取 `ctx.requesterSenderId`，`source-registry` 那份只作兜底，并把**取值来源**打进日志。
`chatId` / `chatType` 仍取自我们自己的 registry——core 的 sessionKey 会把 peer id 强制小写，而企微 `chat_id` 大小写敏感（官方在同一处留了 `93006 invalid chatid` 的警告）。

## 二、我漏抄了官方的诊断行——这正是这一轮定位不了的直接原因

官方在 `sendRawJsonRpc` 里逐次打印「本次请求带没带身份」：

```js
console.log(`${LOG_TAG} sendRawJsonRpc → ${body.method} | ${WECOM_USERID_HEADER}: ${headers[...] ?? "(not set)"}`);
```

我没抄。出问题时第一件要确认的就是这个，没有它只能靠猜。现已补上，并加了两条同类诊断（都不改 wire 行为）：`category` 不在官方 `biz_type` 取值表内时告警（**仅提示，仍原样透传**）、业务错误落日志时带上本次 userid 与企微原始返回（截断 600 字符）。

## 三、撤掉我自己加的 `tools/list` 限幅——它在现网就会误伤

现网 `action=list category=doc` 的实测：**只有 19 个工具就触发了 `truncated: true`**，返回里没有 `inputSchema`。也就是模型调 `sheet_get_info` 时**只能猜参数名**。

这个 32KB 上限是我在 `-13` 自己加的，官方没有。我当初按官方文档估算 `doc` 品类有 60+ 工具据此定阈值，而现网这套 Server 只有 19 个、schema 却更大。**一个凭估算定下、在真实规模上就会误伤的保护，不如没有**——已删除，`tools/list` 恢复为完整 schema，与官方一致。`method` 前缀过滤保留（可选，默认行为与官方逐字节相同）。

## 四、顺带确认：现网的工具名与官方文档不是同一代

| 现网 Server 实际暴露 | 官方文档（2026-08-13） |
| --- | --- |
| `create_doc` | `doc_create` |
| `sheet_get_info` | `sheet_get` |
| `sheet_append_data` | `sheet_rows_append` |
| `smartsheet_add_records` | `smartsheet_records_add` |
| `edit_doc_content` | `doc_contents_append` |

命名规则整个反过来（动词在前 vs 在后）。结论：那份 `biz_type` 取值表可信，但**工具层面不能拿文档当准，只能以 `action=list` 的实际返回为准**。我此前据文档判断「`sheet_get_info` 不存在」，对这套部署不成立。

## `x-openclaw-wecom-userid` 的证据状态（重要）

| 问题 | 结论 |
| --- | --- |
| 官方**文档**里有吗 | **没有**。MCP / CLI / 长连接全部文档中一次都未出现 |
| 官方**代码**里有吗 | **有**。`@wecom/wecom-openclaw-plugin@2026.7.2`（企微团队发布）`src/mcp/transport.js`，注释：「请求 MCP Server 时透传可信企业微信 userid 的 header 名」，每次请求（含 `initialize`）都发 |
| 是第三方自己编的吗 | **不是**。写它的是企微团队本人，发往的是企微自己的 MCP Server |
| CLI 能否旁证 | **不能**。CLI 用成员自己的凭据，二进制里 `userid` 零出现；其中的 `x-wecom-*` 是文件/输出格式标记（`x-wecom-file-save`、`x-wecom-octet-stream`），不是 MCP 头 |
| 有更新的参考吗 | **没有**。`2026.7.2` 是最后一个带 MCP 的官方版本，`2026.8.17-beta.1` 起 `src/mcp/` 已整体删除 |

`x-openclaw-` 这个前缀不代表它是外人发明的——更合理的解释是企微的 MCP 网关**为 OpenClaw 这条接入路径定义的专用头**。

**残余不确定必须写明**：只能证明「企微自己的客户端在发」，无法从文档证明「服务端确实认」。风险为零（HTTP 服务端忽略不认识的头，发了不会弄坏任何现在能用的东西），能否修好是**中等把握**。

## 真机验证要看什么

装上后触发一次之前失败的读取，看 `[wecom-mcp]` 日志：

```
tool ready account=project userid=… useridFrom=ctx.requesterSenderId chatId=… chatType=…
rpc → tools/call x-openclaw-wecom-userid=…
```

- `useridFrom=ctx.requesterSenderId` 且调用成功 → 收工，随后打 tag 发布。
