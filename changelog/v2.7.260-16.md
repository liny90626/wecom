## 一、根因：两条签发路径指向的是两台不同的 MCP Server

用现网真实地址逐个探测八个能力后，结论是决定性的：

| 签发路径 | 对端 | `doc` 的工具 |
| --- | --- | --- |
| 后台「查看使用方式」`/mcp/v2/bot/<biz_type>?apikey=…` | 「动态\* MCP」**v1.0.5** | **62 个新一代**：`doc_create` / `sheet_get` / `smartsheet_records_add` / `smartpage_*` |
| `aibot_get_mcp_config`（机器人长连接） | 旧一代 | **19 个旧一代**：`create_doc` / `sheet_get_info` / `smartsheet_add_records` |

**决定性证据**：后台地址的返回里，服务端**自报身份**——

> 机器人身份：…／**授权真人用户身份：…**
> 真人授权用户创建或拥有的数据你可以进行读取、查询或下载，但你只能写入或修改机器人创建或拥有的数据。

也就是说 **授权是内嵌在 `apikey` 里的**，不是靠请求头传的。`aibot_get_mcp_config` 签发的地址**没有绑定真人用户**，所以对成员拥有的文档一律 `851003`；而品类级的 `tools/list` 不需要真人授权，因此能过。**这就是「list 通、单文档不通」的全部原因。**

实测 `doc_search` 在后台地址上返回了真实文档内容，链路完全通。

> 顺带修正一个此前的误判：MCP 层的 docid 是 `e3_…` 形态，与 wedoc REST 的 `dcLdPZ…` 不是一套——之前那次 `sheet_get` 报 `640027 参数错误` 正是因此，与权限无关。

## 三、本次改动

1. **`bot.mcpServers` 从「排查探针」升格为推荐配置**。使用者已验证：取消授权再重新授权，`apikey` **不变**，可安全写入配置。

   ```jsonc
   "bot": {
     "ws": { "botId": "…", "secret": "…" },
     "mcpServers": {
       "doc":      "https://qyapi.weixin.qq.com/mcp/v2/bot/doc?apikey=…",
       "msg":      "https://qyapi.weixin.qq.com/mcp/v2/bot/msg?apikey=…",
       "mail":     "https://qyapi.weixin.qq.com/mcp/v2/bot/mail?apikey=…",
       "todo":     "https://qyapi.weixin.qq.com/mcp/v2/bot/todo?apikey=…",
       "schedule": "https://qyapi.weixin.qq.com/mcp/v2/bot/schedule?apikey=…",
       "meeting":  "https://qyapi.weixin.qq.com/mcp/v2/bot/meeting?apikey=…",
       "disk":     "https://qyapi.weixin.qq.com/mcp/v2/bot/disk?apikey=…",
       "contact":  "https://qyapi.weixin.qq.com/mcp/v2/bot/contact?apikey=…"
     }
   }
   ```

   配了的品类直接用该地址，没配的仍走 `aibot_get_mcp_config`，行为逐字节不变。**传输层与工具层本就是能力无关的**，因此「支持全部八个能力」不需要任何额外代码。

2. **恢复 `tools/list` 限幅，阈值 48 KB 来自实测**。除 `doc` 外最大的 `mail` 才 12.8 KB，而 `doc` 是它的 22 倍，阈值落在极宽的间隔里。超限时退回「名称 + 说明」索引（`doc` 仅 8.3 KB）并列出可用前缀；按前缀取分别是 `doc_` 38 KB、`sheet_` 50 KB、`smartsheet_` 191 KB、`smartpage_` 8.5 KB、`media_` 1 KB。

   > `-13` 我按官方文档「估算」定过 32 KB，结果在旧一代 Server 的 19 个工具上就误伤，`-15` 因此整段删除。这次的数字是**量出来的**，不是猜的。

3. **`initialize` 后把对端 `serverInfo`（名字/版本）打进日志**——有这行，当初一眼就能看出是两台不同的 Server，不必绕这么多弯。

## 边界说明

- **本轮改动尚未在插件内做真机回归**：根因与链路是用独立探针在真实端点上验证的，但「装上插件后端到端跑通」还需你确认。
- **`aibot_get_mcp_config` 仍是没配置时的默认路径**，它签发的仍是那台没有真人授权的旧 Server。理想终局是让它也签发带授权的地址（其请求体目前只有 `biz_type` + `plugin_version`，不含任何成员身份），但这取决于企微侧。
- **官方 4 个拦截器仍未移植**：`msg-media`（`get_msg_media` base64 → 本地文件）、`smartpage-create` / `smartpage-export`、`smartsheet-upload`。三个属于 `doc`，一个属于 `msg`。开新能力本身不需要它们，但涉及大 payload / 本地文件的操作会缺这层处理。
- 上游 `YanHaidao/wecom` 的新提交仍未合并。
