# v2.7.260-2（2026-08-01，LinKy fork 维护版）

发布标签 `released/2.7.260-2`。本版根治两件来自同一条 Bot WS 失败链的问题：上一轮已完成后，新消息偶发被误报为「本次回复投递中断」；同一个 `WeCom Bot WS reply produced no visible output` 又会被后台记录两次。

> **版本号说明**：上游基线仍为 `2.7.260`，因此构建号从 `2.7.260-1` 递增到 `2.7.260-2`。

---

## 一、完成态释放竞态不再被误判为投递失败

OpenClaw 2026.6.11 / 2026.7.1 的 reply-operation busy 与 inbound dedupe 都可能返回相同的 **flagless zero**：`queuedFinal=false`、三类 count 全为 0，且没有 busy 标记。配置允许 silent reply 时，一个已经被核心接收、但有意不产生可见正文的回合也会返回这个形状。

旧插件在核心返回后再查询 active run：查到就按 busy 重试，查不到就抛 `WeComReplyNoVisibleOutputError`。当上一轮刚完成、reply operation 正在提交终态时，它可能在「核心返回」与「active 查询」之间释放；这个瞬时状态因此被错误地当成「本次新指令没有产出」。这是一个确定的 TOCTOU，而不是网络偶发失败。

修复直接改用**本次调用的接收事实**：

- OpenClaw 6.11 / 7.1 都会通过 `onAgentRunStart` 证明本次启动了 agent；7.1 还会通过 `onTurnAdopted` 证明消息已被 steer。即使 active run 随后释放，接收事实也不会消失。
- 没有触发接收回调的 flagless zero 继续沿用既有的**单次 500ms 有界重试**；第二次仍未接收才提示用户确认新指令未执行后重试。
- 这条重试不再 drain。因为 flagless zero 也可能来自 dedupe，按 session 身份中止可能误杀正在正常处理同一消息的 run；明确的 session-init conflict 仍保留原有 drain。
- `beforeAgentRunBlocked` 和真正启动 agent 后产生的 `noVisibleReplyFallbackEligible` 零输出仍按失败处理，不会被 silent-reply 分支掩盖。

active-run 查询仍保留为 6.11 对「并入既有 run」的兼容信号和日志诊断，但不再被用来反推本次 flagless-zero 是否已接收。

## 二、同一个 Bot WS 错误只记录一次

旧链路的 `failAndThrow(error)` 先调用 tracked `replyHandle.fail(error)`：这里已经记录一次 operational issue，并让 Bot WS handle 发送一次失败提示；同一个 error 随后继续逃到 `BotWsSdkAdapter.reportFrameError`，frame 边界又记录一次。因此两条完全相同的英文后台提示来自**同一个异常跨过两个记录边界**，并不是模型失败了两次。

修复只收口同时满足以下条件的异常：

- transport 是 Bot WS；
- tracked `replyHandle.fail()` 已成功完成；
- runtime catch 到的仍是同一个错误对象。

未经过 fail、fail 尚未完成、对象不同以及非 Bot WS 的异常仍然上抛。这样只去掉第二次重复记录，不新增全局异常保护，也不会吞掉真正的 frame/runtime 崩溃。

## 边界说明

本版只修改三个生产文件及其三份回归测试，没有引入新的重试阶梯、熔断器或全局保护层。企微真实网关下的终态释放时序仍需发布后通过 `dispatch-handoff-retry reason=busy-result`、`dispatch-adopted-silent-reply` 与 `dispatch-failure-contained` 日志持续观察。
