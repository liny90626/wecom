# v2.7.260-21（2026-08-28，LinKy fork）

发布标签 `released/2.7.260-21`。本版有两块内容：一次针对上一轮候选的对抗式评审（三处修复），以及按 `goal.md` 补齐的官方功能对齐（模板卡片出站能力等）。

## 一、对抗式评审：上一轮候选的两条修复都没修好

工作区候选声称修好了「冻结状态定时器空转」与「deferred 回合伪完成」。逐条复现后，**两条都没修好，第二条还引入了内容丢失**。

### 1. 冻结状态定时器仍会 0ms 空转

候选给 `startPreviewStatusInterval` 加了五个守卫，漏掉一条路径：**流仍可写、ACK 一直不回**（`streamAckUnreliable` 锁死而 `streamUpdateUnreliable` 仍为 false）。

实测该场景 200 次 timer 步进内出现 **98 个 0ms 定时器**，只推进 79.6 秒虚拟时间，`replyStream` 被调用 **297 次**——约 3.7 次/虚拟秒，而设计节奏是 60 秒一帧。

根因是车道语义不一致：冻结状态车道的状态槽只在**确认送达**时消费，而同文件另外两条车道（`sendPlaceholder` 的 `claimLongTaskStatusSlot`、`maybeSendPreviewExpiredNotice` 的 `markLongTaskStatusPainted`）都是**派发即消费**。一帧未确认 → 槽位仍到期 → 重挂时 `Math.max(0, nextDue - now)` 算出 0 → 立即重进。

修复：`startPreviewStatusInterval` 增加 `minDelayMs`。「跑完一轮之后」的两个重挂点（自身 `.finally`、`flushPendingPreview` 的 `finally`）传 `LONG_TASK_STATUS_INTERVAL_MS`；冻结时首次挂载仍传 0，保证 8 分钟后才开始产出正文的回合不被额外拖慢一分钟。修复后 0 个 0ms 定时器，200 步覆盖 2.6 小时虚拟时间，`replyStream` 125 次。

> 先尝试过「派发即占用槽位」的对齐写法。它会让死流场景下推送车道的接管**推迟整整一分钟**（8:00 静默到 9:00），5 条既有用例变红，已放弃。

### 2. `closeDeferred` 不再关闭企微流

探针对比：deferred 回合下基线发 `replyStream(<用户已看到的文本>, finish=true)`，候选**什么都不发**。企微流不收尾，气泡在整个窗口期（约 6 分钟）保持「正在生成」，而该回合其实已结束；仓库其余所有终态路径都会发 `finish=true`。

修复：`closeDeferred` 改走既有 `closeOpenedStreamSilently(lastPreviewText)`——它会 settle、跳过死流与不可信流、等待 pending ACK，且不追加任何完成文案。编排层同时补 `await sealProgress()`，否则会在过程帧还排队时收尾，丢掉最后一步并按过期文本关流。

### 3. `closeDeferred` 静默丢掉模型已产出的正文

探针对比：两段 block、第一段送达后窗口关闭时，基线推送 `继续输出：\n\n第二段未送达的尾巴。`，候选**推送为空**——第二段永远到不了用户。这比它想修的问题更严重，也违反既定取舍「宁可有限重复，不静默丢答案」。

真实边界是：那句 `最终回复已完成，以上预览内容即为完整回复。` 只在 **remainder 为空**时由 `resolveStreamFallbackText` 产生；remainder 非空时基线发的是 `继续输出：…`，既无虚假声明又确有价值。

修复：`closeDeferred` 返回 `boolean`。回合仍有用户未看到的正文时返回 `false`，编排层落回既有 final 通道（分片、重试、书签、去重都在那里，不重写）；确实无话可说时才关流。

候选原有的两条 deferred 用例**去掉生产改动后照样通过**，不具判别力，已改写为断言「收尾帧 `finish=true` 且不含完成文案」。

## 二、模板卡片出站能力（此前只发了技能，没有实现）

`wecom-send-template-card` 技能随包发布已久，技能原文写着「插件自动提取并发送」，而本 fork **没有任何出站卡片实现**——模型照技能吐出的 JSON 代码块会被当普通 markdown 发给用户。本版按官方 `2026.8.17` 移植补齐。

新增 `src/capability/card/{parser,manager}.ts`（对应官方 `template-card-parser.ts` 731 行 + `template-card-manager.ts` 295 行），三个接入点：

- **抽取与发送**：final 文本中的 ```json 卡片块被抽出、按企微 API 归一化（字段类型修正、必填补全、简化格式 → API 格式、`task_id` 重新生成）后经 `sendMessage(msgtype: template_card)` 单独推送，正文只留剩余文字。解析失败或 `card_type` 不合法的代码块**保留在正文里**——那多半是模型贴给用户看的普通 JSON。
- **流式遮罩**：`renderPreviewFrame` 统一遮罩，已闭合的卡片块替换为占位文案、未闭合的尾巴截断。放在这一层而不是某个调用点，是为了让正文预览、冻结状态、超时冻结三条预览车道行为一致。
- **交互回调**：`template_card_event` 先更新卡片本身（禁用控件、提交按钮改「已提交」、勾上选中项）再照常派发给 agent，与官方一致。卡片缓存进程内、TTL 24 小时、上限 300 条。

与官方有意保留的差异：

| 项 | 官方 | 本 fork | 原因 |
| --- | --- | --- | --- |
| 日志 | 打印整张卡片 JSON | 只记数量、`card_type`、`task_id` | 卡片正文含用户内容 |
| 发送失败 | 仅记日志 | 正文追加「⚠️ 有 N 张卡片消息发送失败。」 | JSON 此时已从正文移除，静默等于这一轮看着答完了、用户却什么也没收到 |
| 核心字段缺失 | 仅告警仍发送 | 跳过该张并记 `reason=missing-<field>` | 必然被服务端拒绝，发它只是白跑一次 |
| 群聊 | 不带 `chat_type` | 带 `chat_type` | 与本 fork 其它主动推送一致（官方文档：不填按群聊处理） |

`index.ts` 同步注入卡片能力的 system context。

## 三、未完成的回合不再宣称完成

deferred 回合走主动推送时，尾巴文本后面仍会挂 `（回复完毕）`。来源不是 `finalAppendCompletionMarker`，而是 `deliverNormalFinalViaStream` 里的 `fallbackAppendCompletionMarker = !options.isError`——推送没有气泡上下文，正常回合确实需要这个标记表示答案到此为止，但 deferred 回合的答案还在后面。

修复：编排层把 `channelData.wecomDeferredTurn` 传给 transport，transport 据此同时压掉 fallback 标记与 reasoning-only 的标记提升。正文该推的照推，只是不再宣称完成。

## 四、入站附件超限给出可操作提示

复现确认用户实际看到的是 `response body too large (>83886080 bytes)`——既不说上限是多少，也不说去哪儿改。

修复：`readResponseBodyAsBuffer` 抛类型化的 `ResponseBodyTooLargeError`（把「文件太大」与「网络断了」分开，后者不能被伪装成前者）；`WecomMediaService` 把它翻译成写明上限与去向的中文提示，并在调用核心媒体库之前先自检 buffer 大小——核心库自己的拒绝文案同样不可操作。

## 八、边界

- Windows x64/ARM64 真机与真实企业微信网关/客户端仍未验收；官方没有 Windows ARM64 CLI 平台包。模板卡片尤其需要真机确认渲染与交互回调。
- 入站视频首帧提取（ffmpeg）明确不做，理由见 `goal.md`：官方自己的 Bot WS 主链路也没有，且会引入装了才生效的硬外部依赖。
- 仓库 `package-lock.json` 为 0 字节，`npm audit --omit=dev` 返回 `ENOLOCK`；生成 lockfile 会改变安装解析，需用户点头，本轮未擅自生成。
