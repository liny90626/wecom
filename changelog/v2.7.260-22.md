# v2.7.260-22（2026-08-29，LinKy fork）

发布标签 `released/2.7.260-22`。两处都来自真机反馈：卡片交互回调进 agent 通道的形态不可用；长任务超时后**唯一有用的那句报错被去重逻辑吞掉**。

## 零、长任务超时只报「LLM request failed.」

现网日志（2026-08-29 09:07）：

~~~text
09:07:29 warn agent/embedded  embedded run timeout: runId=… timeoutMs=600000
09:07:33 warn [wecom-reply] error-final … elapsedMs=605429 text="收到，任务拆成三块…"
09:07:33 outbound kind=final summary="bot-ws LLM request failed."
09:07:33 warn [wecom-b3] final-skip second-distinct …
09:07:33 outbound kind=final summary="bot-ws Request timed out before a response was generated. Please try again, or increase `agents.defaults.timeoutSeconds` in you…"
~~~

OpenClaw 的 embedded run 命中自己的 600 秒上限后**连发两条 final**：先是通用的 `LLM request failed.`，再是点名配置项的 `Request timed out … increase agents.defaults.timeoutSeconds`。

`markFinalDelivered` 把第二条当成重复投递丢掉了——用户于是只看到「任务未完成：LLM request failed.」，而唯一说清楚该改哪个开关的那句话，从来没到过用户眼前。

那段代码的注释原文是「no WeCom case has been observed, and this line is what would prove one」。这份日志就是那个 case。

**修复**：去重是为「同一答案的重试」建的，只有在已投递的那条**就是答案**时才可以丢弃后续。已投递的是错误通知时，错误从来不是最终结论——放行后续 final，作为独立消息送达。已投递的是正常答案时行为不变，仍然丢弃。

顺带把该 handle 的分片投递账本在放行时清零，避免后继消息复用前一条的 chunk 进度。

> 需要说明：600 秒上限本身是 OpenClaw 的 `agents.defaults.timeoutSeconds`，不是插件能改的。插件的责任是**把说明这件事的那句话送到**，这一点此前没做到。

## 一、卡片交互回调进 agent 通道的形态不可用

### 根因

`2.7.260-21` 的卡片渲染与交互更新真机验证通过，但用户点选提交后，机器人会多回一句「已收到 templatecardevent 事件」。

`template_card_event` 在事件白名单里（更新完卡片后照常派发给 agent，与官方一致），但本 fork 的入站映射把所有事件统一渲染成 `[event:<类型>]`。模型收到的就是 `[event:template_card_event]` 这么一个占位串——它既不知道用户选了什么，也没有别的可说，只能回一句「已收到某某事件」。

**提问的人因此永远拿不到答案。** 交互卡片存在的意义就是把选择送回给 agent，这条链路断了，卡片就只是个好看的静态控件。

官方 `message-parser.ts` 里有 `buildTemplateCardEventText`，注释写明「这样后续 Agent 可以直接从 question_key / option_id 中理解用户的真实选择」——我们移植 `2026.8.17` 时漏了这一段。

### 修复

新增 `describeTemplateCardEvent`，把回调渲染成模型看得懂的文本：

~~~text
[企业微信模板卡片回调]
card_title(卡片标题): 午饭吃什么
card_type(卡片类型): vote_interaction
task_id(任务 id): task_vote_…
selected_items(选择项):
- 午饭吃什么: 饭
~~~

比官方多做一步：官方只给原始的 `question_key` / `option_id`（形如 `vote_1787…: b`），模型仍得猜 `b` 是什么。发出去的卡片本来就在缓存里（交互更新要用），顺手把 id 还原成标题与选项原文；缓存不在（进程重启过）时退回原始 id，与官方一致。按钮类回调同理，`event_key` 会带上按钮文案。

其余事件类型不受影响，仍是 `[event:<类型>]`。

### 边界确认

- 卡片事件的 `inboundKind` 是 `template-card-event`，在 transport 侧按 `isEvent` 处理，回复走主动推送而不占流——该 `req_id` 要留给 `updateTemplateCard`（企微要求 5 秒内回复），两者不会互相抢。
- 群聊里每个人点一次就是一轮 agent，与官方行为一致。若要改成静默，是把 `template_card_event` 移出 `DISPATCHABLE_EVENT_TYPES` 的一行改动，但那样 agent 就永远收不到选择结果。
