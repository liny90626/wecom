# v2.7.260-5（2026-08-07，LinKy fork 维护版）

发布标签 `released/2.7.260-5`。本版根治两条相互独立的 Bot WS 故障链：OpenClaw 已产生结构化任务进度、但插件未向企微转发；相邻回合复用同一 `req_id` 时，旧回调流会覆盖新气泡，迟到 ACK 还可能永久吞掉前一条内容。

> **版本边界**：开发与自测只使用 OpenClaw **2026.7.1-2**，不再执行双版本矩阵。`peerDependencies.openclaw` 继续保留 `^2026.6.11` 安装兼容范围，但不代表对旧版进行本轮验证。未执行 `npm publish`。

## 一、真实 OpenClaw 任务进度不再在插件入口丢失

旧实现只转发 preamble、reasoning、Fast 和经过正文过滤的普通 tool result。OpenClaw 2026.7.1-2 的 item/tool/command/plan/approval/patch/compaction 生命周期已经在运行，但这些结构化事件没有进入 Bot WS 可见进度通道；因此纯工具长任务可以一直只显示插件自造的长任务提示，最终失败时用户仍看不到 OpenClaw 实际执行到了哪里。

修复后：

- `dispatchRuntimeReply` 接收 OpenClaw 的结构化 item 和 lifecycle 回调，并复用官方 channel progress formatter 生成最多 4 行状态快照。
- 只保留受控类别、工具名和状态；命令文本、参数、文件路径、搜索词、审批内容、工具返回值等敏感载荷不进入企微。未知名称统一降级为 `tool_call` / `api`，不会原样外泄。
- item、tool、command、plan、approval、patch、compaction 的开始、更新、完成、失败、阻塞与取消状态可以原位合并；同一 tool 的通用/专用事件共用标识，避免重复行。
- 正文、reasoning、preamble、结构化进度与 Fast 各自记账；瞬态状态不冒充正文，也不进入 final。长任务心跳会保留最新真实过程，而不是重新覆盖成一条纯计时文案。
- 过滤掉的普通 tool result 仍不算有效运行产出，原有 fallback-eligible zero-output 失败语义不被放宽。

在 `109c72e` 的原生产实现上，真实 OpenClaw dispatcher 探针只有失败 final，没有 `Exec: running`；当前候选会先投递净化后的真实执行状态，再按原语义交付失败 final。

## 二、复用 `req_id` 不再覆盖相邻气泡

企微 SDK 按 `req_id` 维护回调回复队列，ACK 也只按 `req_id` 匹配。此前适配器默认每个入站帧的 `req_id` 都唯一：当企微复用同一值时，后一个回合会继续写前一个回合的气泡；若前一帧超时后的 ACK 迟到，它还会错误结算新队首，使前一条内容永久消失。文件+文字合并窗口让这个时序更容易出现，但根因是回调流缺少动态所有权，而不是附件合并本身。

修复后：

- 每条回调流用 `messageId + ownerToken` 认领 `req_id`，认领有效期为 8 分钟；同一 `req_id` 同时只能有一个当前 owner。
- `req_id` 冲突、原消息重投、缺失 ID、认领表满，以及 TTL 到期但 SDK 仍有待结算 ACK 时均 fail closed：不再触碰不安全回调流，直接走现有 active push。
- 认领表满时只清理已过期项，不淘汰仍可能重绘气泡的活跃流。
- 所有权丢失一旦发生即永久锁存；progress、长任务心跳、final、failure、welcome 及等待 pending ACK 的路径都会重新确认，旧 handle 不会稍后“恢复”为当前 owner。
- final 去重加入 owner generation，既保留同一 handle 内的去重，也不会把不同 owner 的相同正文误判为重复。
- 网关模拟修正为真实 SDK 语义：迟到 ACK 会结算当前同 `req_id` 队首，而不是仍绑定原 Promise。

跨层集成回归覆盖文件后文字、丢 ACK 后接管、相邻唯一 `req_id`、相邻复用 `req_id`，以及复用 `req_id + 6 秒迟到 ACK`。在原生产实现上，复用值会覆盖前一气泡，迟到 ACK 场景会永久丢失前一条内容；当前候选保留两条可见回复。

## 三、同源边界加固

- thinking 和冻结预览在 UTF-16 字符边界裁剪时不再切断 emoji 代理对，避免生成损坏字符。
- 瞬态过程的可见书签与正文书签分离；流死亡后的 background notice 可继续携带新进度，且不会错误推进正文书签。
- 所有权丢失期间到达的晚预览不能再改变正文书签；取消、ACK 等待与 welcome/failure 均继承同一 fail-closed 规则。
