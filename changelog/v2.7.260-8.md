## 一、`🧰 Tool Call` / `🛠️ Exec` 这类提示为什么必须整条删掉

**现象**：长任务和短任务的过程气泡里都会出现工具调用提示。

**根因不是「渲染得不好」，而是这条通道结构上不可能有信息量。** `2.7.260-5` 为了让长任务显示真实过程，接入了 OpenClaw 的 7 个 lifecycle 回调（`onToolStart` / `onCommandOutput` / `onPlanUpdate` / `onApprovalEvent` / `onPatchSummary` / `onCompactionStart` / `onCompactionEnd`）和非 preamble 的 `onItemEvent`。但按禁改 35，命令文本、参数、路径、搜索词、审批内容、工具返回值**全部不可外发**，工具名也必须降级成白名单里的通用值。把真实事件喂进官方 formatter 后，实测输出只有：

```
🧰 Tool Call: running
🛠️ Exec
🧰 Tool Call: running
```

即：**脱敏之后剩下的就是「有个工具在跑」**。而「有个工具在跑」这件事，8 分钟长任务心跳（`【长任务处理中，请勿打断，已用时8m00s】`）已经在说了，且不占正文预算。所以这条通道提供的是纯噪声。

**处置**：整条删除——7 个回调、`allowToolLifecycleWhenProgressHidden` 的渲染用途、kind/status/toolName 三张归一化表、`structured-item` 载荷类型、以及 `reply.ts`、`reply-visibility.ts` 里对应的分支。

**保留的唯一一点**：`onToolStart` 仍然订阅，但**只置 `runActivityObserved`，不产生任何投递**。这是刻意的：删掉它之后，一个「只跑工具、没有可见输出、被 OpenClaw 判为 deferred」的回合会被误判成空回合，给用户回一条 `WeComReplyNoVisibleOutputError`。该退化已用定向用例复现（去掉这 3 行 → 用例直接抛错），因此这不是保护，是分诊需要的事实证据。未知/内部 item kind 仍然不算证据，既有用例照旧守着。

## 二、重复的文字段落：过程文字被当成了累积清单

**现象**：过程气泡里出现重复、层层堆叠的段落，`2.7.260-6`（跨 item 整段去重）和 `2.7.260-7`（快照内按可见行去重）都没根治。

**根因（源码级）**：OpenClaw 的 CLI 后端在 `execute.runtime` 里这样发过程文字——

```js
let commentaryCounter = 0;
const emitCliCommentaryText = (text) => {
  commentaryCounter += 1;
  emitAgentEvent({ stream: "item", data: {
    kind: "preamble",
    itemId: `commentary-${params.runId}-${commentaryCounter}`,   // ← 每段都是新 id
    progressText: transformedText,
  }});
};
```

而它的触发点是 `content_block_start` 遇到 `tool_use`（`claude-live-session`）：**模型每调一次工具，工具之前那段自述就被 flush 成一条新的 commentary，itemId 每次都变**。

插件这边把 `preambleItemOrder` 里**所有** item 的文本按首次出现顺序换行拼接。于是一个调了 6 次工具的回合，气泡里就叠了 6 段自述。模型跨步骤的自述天然高度相似（「我先看看 X」「我再看看 X 的配置」），所以看起来就是「重复的文字段落」——但它们不是同一个字符串，v6 的整段 `Set` 和 v7 的按行 `Set` 都吃不掉。

**这不只是难看，还会吃掉答案。** 气泡按 `composePreviewSuffixWithinLimits(prefix=正文, suffix=过程)` 合成，**suffix 先按全额预算渲染，正文只拿剩下的**。所以自述堆得越高，用户能看到的答案正文被截得越短。

**修复**：preamble 恢复它本来的语义——**当前步骤的快照，不是清单**。`preambleTextByItem` / `preambleItemOrder` / `anonymousPreambleItem` 三个结构合并成一个 `currentPreambleText`，最新值直接覆盖；文本没变就不发帧。itemId 不再参与判定（它本来就是每段递增的噪声）。

连带删除：v6 的跨 item `Set<string>` 去重、v7 的 `composeTransientProgressSnapshot` 按行去重。根因消失后它们就是对模型原文的多余改写——按「所有代码都为根因存在」的要求，一并移除，插件不再擅自删改模型写下的句子。

`reply.ts` 里 preamble 与 fast-mode 两个完全相同的分支也合并成一个。

## 三、这对速度与稳定性的实际影响

- **帧数**：一个 6 步工具回合，旧实现每个 lifecycle 边沿都可能推帧（18 个事件），新实现只在自述变化时推（≤6 帧），定向用例已固化上界。
- **答案延迟**：企微 SDK 每个 `req_id` 只有**一个串行回执槽**，final 发送前要等 `waitForPendingReplyAckToClear`（最长 5.5s）。过程帧越少，final 撞上待回执的概率越低——**这是直接的答复提速**，不是副作用。
- **正文完整度**：过程不再无界增长，正文不再被挤出 3500 字符预算。
- **分诊语义**：`runActivityObserved` 的证据面通过 `onToolStart` 保持不变，deferred 回合不会退化成错误提示。
