# 3.0.0-13（2026-10-01，LinKy fork）

生产 OpenClaw 正式升级到 **2026.9.7**，本版是对应的插件兼容修复。开发基线随之改为 9.7；2026.7.1-2 退出生产，只作为兼容底线保留（仍需能编译、测试通过）。

## 9.7 兼容修复

- **9.7 删除了 `onTurnAdopted`，被并入运行中任务的消息会被重发并收到假通知。**
  - 9.7 把消息被并入正在运行的任务写在分发结果上（`deferredToActiveRun: "steer" | "followup"`），不再调用 `onTurnAdopted`，也不设置「无可见回复」标记。
  - 插件因此落到「核心无标记零结果」分支：先把核心已经受理的消息**重发一次**，再给用户推「这条消息没有被处理」或「任务冲突」的假通知。
  - 现在看到 `deferredToActiveRun` 就发「已并入当前任务」，不再重试。
  - 7.1-2 上继续使用 `onTurnAdopted`。
  - 9.7 另有 `deliberateSilentTerminalReply`（刻意静默），**有意不采用**：群聊配置了 `silentReply.group="allow"` 时，被核心拒绝的消息也会标成静默；真正的静默轮次会启动 agent run，已由 `onAgentRunStart` 覆盖（对抗式审查发现）。
- **离开即将删除的 SDK 子路径。** 9.7 把 `openclaw/plugin-sdk/infra-runtime` 列为 2026-10-01 之后待删除。插件只从里面取 `resolvePreferredOpenClawTmpDir`，改为从 7.1-2 和 9.7 都导出的 `plugin-sdk/temp-path` 引入。导入白名单与兼容检查里残留的 `file-access-runtime` 类型补丁（3.0.0-6 起已无人引用）一并删除。
- **附件同时带上新的 `media` 字段。** 9.7 把旧的 `MediaPath` / `MediaPaths` / `MediaTypes` 列为待删除（`media-legacy-projection`，目标 2026-10-01），新字段是有序的 `media` 列表。旧字段一旦删除，附件就到不了 agent。
  - 现在 Bot WS 与 webhook 两条入站链路都在旧字段旁同时传 `media`。
  - 9.7 会按位置合并两种写法，已实测不会重复出附件；7.1-2 没有这个字段，会直接忽略。
- **9.7 下真实分发器测试互相干扰（仅测试）。** 9.7 在进程内缓存第一次打开的状态库，之后再改 `OPENCLAW_STATE_DIR` 不再生效。测试原先每个用例新建、删除自己的目录，第二个用例起就会撞上已删除的库（ENOENT）。改为同一测试文件共用一个目录，测完统一删除；首个用例冷启动约 4 秒，放宽超时。

## 移植官方插件

- 对照官方 `WecomTeam/wecom-openclaw-plugin`：
  - GitHub 自 2026.8.17（`3b1cbe3`）后没有新提交；
  - npm 上的 2026.9.15 运行代码与 8.17 相同，只改了两个技能，没有做任何 OpenClaw 9.x 适配。
- **`wecomcli-doc` 新建文档流程（移植）。**
  - 8.17 的 `build_docx.py` 依赖 `WECOMAGENT_WRITABLE_DIRS`。这是企微自家 agent 宿主的沙箱变量，OpenClaw 从不设置，所以「从零新建 doc 文档」在 OpenClaw 下必然失败（已复现：`failed to pick output path`）。
  - 9.15 改为把 `.docx` 写到 JSONL 旁的 `docx/` 子目录：只新建、不覆盖，文件名经过清洗；脚本只读取指定的 JSONL，不执行外部命令、不联网。
  - 原样移植三个文件，只把上游文档里指向不存在的 `wecom-unified` 目录的路径改回我们的实际位置。
- **`wecomcli-sheet` 新建表格流程（移植）。** 9.15 改为「用 `openpyxl` 在本地生成 `.xlsx` → 校验 → `wecom-cli sheet import` 导入」，不再用 `sheet create` 直接写入单元格数据。`sheet import` 在锁定的 `@wecom/cli` 1.2.0 中已有。依赖生产机的 Python + `openpyxl`，维护者已确认生产机具备。原样移植，只清理了行尾空格（与本 fork 其他技能文件一致）。
- 评估后不移植的：
  - 社区 PR #188（`turnAdoptionLifecycle` 释放会话队列）：不移植。官方是逐会话排队，我们是新消息顶替旧任务，没有可释放的队列。在 9.7 上传这个字段还会让核心把新消息并入或排到旧任务后面，与本 fork「新消息接管」的设计相反。
  - `@wecom/cli` 1.2.0 → 1.3.4：不升级，原因见下文「已知限制」。
  - WS 客户端的 `scene` / `plug_version` 参数：只是遥测，不移植。心跳、重连、鉴权失败次数与官方取值一致。

## OpenClaw 侧问题（不在插件修复）

- **9.7 在 Windows 上每条消息都失败：`DataCloneError: #<Object> could not be cloned.`。** 这是 OpenClaw 核心的 bug，与插件无关，官方插件同样会遇到。
  - 原因：核心在 Windows 上把环境变量包成 Proxy（为了不区分大小写），9.7 新增的「回复准入」又把它原样传给工作线程，Proxy 无法跨线程复制。
  - 已在不加载任何插件代码的情况下复现。由维护者在 OpenClaw 侧提 PR 修复，插件不做绕过。

## 已知限制

- **steer 被核心中止时仍提示「已并入」。** 核心先把消息标记为已受理，确认转录失败后中止目标任务，但分发结果仍带 `deferredToActiveRun: "steer"`，用户会看到「已并入当前任务」，实际这条消息被丢弃。7.1-2 的 `onTurnAdopted` 同样如此，频率低，本版不处理。

- `@wecom/cli` 1.3.x 修复了一个隐私问题：1.2.0 的遥测会带上 JSON 修复前后的载荷原文。但 1.3.0 同时把 CLI 的文件读写限制在「当前工作目录 + 系统临时目录」以内。插件以私有状态目录作为 CLI 的工作目录启动它，agent 工作区里的文件（例如新生成的 docx）会被拒绝。要升级，需要先重新设计 CLI 的工作目录。维护者决定**保持 1.2.0**，不升级。
