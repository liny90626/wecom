# 3.0.0-15（2026-10-02，LinKy fork）

生产 OpenClaw 在 2026.9.7 上问题较多，已**回退到 2026.7.1-2**，今后只以 7.1-2 为生产与验证环境，不再考虑其他版本的兼容。本版撤掉只服务于 9.x 的代码，做了一轮对抗式检查与性能、稳定性提升，并对照官方插件补齐了几项能力。

> 版本号说明：`3.0.0-14` 只作为验收候选包发给维护者，没有打 tag、没有发布；其内容全部并入本版。

## 回到 7.1-2

- 开发依赖锁回 `2026.7.1-2`。`npm run compat:check` 默认只检查这一个版本，其他版本需要显式传参，删除了查询 latest 的辅助函数。
- 删除只有 9.x 才会走到的代码（7.1-2 核心不设置这些字段，在 7.1-2 上是死代码）：
  - `deferredToActiveRun` 的判断分支；
  - 附件的 `media` 字段；
  - 测试里共用的状态目录。
- 保留的改动：`temp-path` 子路径（7.1-2 本来就导出），`wecomcli-doc` / `wecomcli-sheet` 新建流程（与 OpenClaw 版本无关）。

## 稳定性修复（对抗式检查发现，均已复现后修复）

- **入站去重表只增不减。** 每个账号的运行时存储会保存每条入站消息：
  - 消息 id 存在 Set 里，永不删除；
  - 完整原始帧（含媒体 URL 与 aeskey）存在一个从没被读取过的 Map 里。
  
  每条消息约占 0.7–2.7 KB，直到账号重启才释放。现在消息 id 只保留 30 分钟去重窗口，按到达顺序清理；未使用的回复上下文与投递任务存储一并删除。
- **重复送达的媒体消息留下关不掉的回复。** 媒体帧在分发前就打开思考气泡，分发器随后判定它是重复消息直接返回，没有任何地方再关闭这个回复。结果是气泡卡在「正在思考中」，之后每 5 分钟推送一次「长任务处理中」，直到网关重启。另外，重复送达的文字还会把一条新媒体合并进一个整体被丢弃的事件。
  
  现在适配层在创建回复之前先查去重表，已处理过的消息直接忽略，并记入审计日志。
- **内部报错原文展示给用户。** 不属于四类已识别错误的失败，会以 `WeCom WS reply failed: <原始错误>` 作为气泡的结束内容，例如媒体解密失败会显示 `...bad decrypt`。
  
  现在一律显示「本次回复投递中断」，原始错误只写日志。本来就写给用户看的「附件超过大小上限」原样展示，不再带英文前缀。
- **长任务的最后一段正文发两遍。** 流窗口失效后，正文走 20 秒一次的主动推送，「已送达正文」的书签只有在推送确认后才前移。OpenClaw 紧接着最后一块发来最终回复，正好落在这次推送的 ACK 等待里，最终回复就按旧书签把最后一段在「继续输出」下又发了一遍。
  
  现在最终回复先等在途的正文推送结束，再计算剩余内容：每段发送都有超时，所以等待一定会结束；这一步放在所有「已被顶替」判断之前。只带过程进度的推送不移动书签，不会拖住最终回复。
- **SDK 放弃重连后恢复太慢。** SDK 用完重连次数（约 3 分钟退避）或多次鉴权失败后会彻底停止，插件只记一行日志，恢复全靠 OpenClaw 健康检查，需要几分钟；健康检查被关闭时则永不恢复。
  
  现在 bot 服务只替换 WS 适配器：从 5 秒开始翻倍退避，上限 5 分钟，最多 10 次，稳定运行 10 分钟后重新计数。同一账号上的 agent 回调与去重状态不受影响（对抗式复审发现，让整个账号任务退出会连带反复重启健康的 agent 回调）。
- **顶号后的行为描述错误。** 收到 `disconnected_event` 后 SDK 不会重连，但 OpenClaw 健康检查会在几分钟内重启账号，所以注释里的「不能重连」不准确；若两处使用同一个 botId，双方会轮流把对方顶下线。注释与审计摘要已改正。断线日志里 `kicked` 一直是 false，现在能正确识别 SDK 的「New connection established」原因。

## 性能提升

- **首段文字 200 字就显示，不再等 800 字。** OpenClaw 分块默认最少 800 字才交出第一段，Bot WS 车道没有覆盖这个默认值（webhook 车道早就覆盖了），测算首屏晚 6–12 秒，不足 800 字的回答完全不会流式显示。维护者确认生产没有配置这一项后，Bot WS 回复在未配置 `agents.defaults.blockStreamingChunk.minChars` 时按 200 字处理；最多 1200 字、按段落切分仍是核心默认，合并发送的门槛随之变为 200。配置了 `minChars` 就以配置为准；其他车道不变。已用 7.1-2 核心的解析函数核对：生效值从 800/800 变为 200/200。
- **思考片段不再逐条写日志。** 每次投递原来写三行日志并刷新一次账号状态，而思考内容按模型增量逐条投递。核心日志每行都是事件循环上的同步文件写入：Linux 实测约 0.9 毫秒一行，Windows 加上杀毒软件只会更慢。长思考过程累计会卡住事件循环数秒，并拖慢 WS ACK 的处理。
  
  现在思考片段不写日志、不刷状态；其他投递合并为一行 `deliver-done`（文本长度、媒体数、耗时、摘要）。
- **媒体在合并窗口内提前下载。** 单发的图片或文件要先等 1 秒的「媒体 + 文字」合并窗口，而下载要等窗口结束、准备会话时才开始，每条都多等最多 1 秒。
  
  现在媒体帧进入等待时就开始下载，后续直接取用：按账号 + 附件 URL 作 key，只取用一次，「附件超限」的提示保留。没人取用的预取在 60 秒后释放，失败也不会产生未处理的 Promise 拒绝。

## 对照官方插件补齐

官方 `WecomTeam/wecom-openclaw-plugin` 自 2026.8.17（`3b1cbe3`）后 git 无新提交，npm 最新仍是 2026.9.15（运行代码与 8.17 相同，技能已在 3.0.0-13 移植）。本轮逐项对照官方运行代码，只补我们确实缺的：

- **一条消息的多个附件全部交给 agent。** 原来只有第一个附件成为 `MediaPath`：一条带 3 张截图的图文消息、或合并进同一轮的多个文件，模型只能看到 1 个。现在最多 8 个附件（与 webhook 车道一致）并行下载，以 `MediaPaths` / `MediaTypes` 交给核心（7.1-2 原生支持，会逐个列出）。只有 1 个附件时传给核心的上下文与原来完全相同。本轮被放弃（被新消息接管、准备超时）时，下载随之中止，不再在后台占用内存。
- **附件下载失败不再吞掉整轮。** 原来解密或下载失败会让整轮以「本次回复投递中断」结束，用户打的字一起丢失。现在与官方一致：文字照常交给 agent，并附一行「[附件读取失败]」（多个失败时注明个数），其余附件不受影响。第一个附件超过大小上限时，仍按原样提示并结束本轮；后面的附件超限只记入这行说明。
- **加密附件下载超时改用配置值。** 原来固定 15 秒，现在用 `media.downloadTimeoutMs`（默认 30 秒，webhook 车道本来就用它），大文件在慢网络下不易超时；上限 45 秒，保证单个文件卡住时降级为说明，而不是撞上 60 秒的准备超时、整轮失败。
- **加密媒体 URL 不再写进给模型的正文。** Bot WS 的媒体 URL 是加密内容，模型拿到也读不了，只会浪费 token 或尝试去抓取。现在正文只保留 `[image]` / `[file]` / `[引用: 文件]` 这类标记，附件本身照常作为媒体传入；webhook 车道不变。
- **文档授权变更事件有了含义。** 成员在授权页改完权限后，agent 原来只收到 `[event:auth_change_event]`。现在按官方写法说明当前授予了哪些文档权限（新建和编辑文档 / 获取成员文档内容），以及能否继续刚才中断的文档操作、缺什么权限该找谁开。
- **Windows 下 `~\` 开头的 `media.localRoots` 能展开到用户目录**（原来只认 `~/`）。

评估后不跟进的官方做法：
- Bot WS 的私聊 / 群聊准入控制（`dmPolicy` / `groupPolicy` / 配对）：本 fork 的 Bot WS 一直不校验发送者，生产依赖这一点；照搬官方默认会拦掉现有用户。
- 鉴权失败后不再自动重试、被顶号后挂起账号等待人工处理：对生产没有收益，后者会让正常的接管也要手动重启。
- `reqid` 持久化、会话排队、SDK 自带下载、文件类型嗅探：我们已有等价或更完整的实现。

## 回归复查

对 3.0.0-13 以来的全部改动再做一次只读回归审查，没有发现会错发、漏发或丢消息的回归，只有两处状态记录的副作用，已修复（官方补齐部分另做一次对抗式审查，采纳了上文的下载中止、45 秒上限与「只有首个附件超限才结束本轮」三条）：
- 顶号断线被记录两次：`disconnected_event` 帧已记一次，随后 SDK 的断线原因又被识别为顶号再记一次，审计日志与状态各多一条。现在同一次顶号只记一次。
- 重复送达在入口被丢弃时，原来记成账号的「最近错误」，状态里会把一次无害的重投显示为错误。现在只写审计日志，与分发器自身丢弃重复消息的做法一致。

## 评估后不改或待决定

- **入站附件文件不会自动清理。** 插件配置里的 `media.retentionHours` / `cleanupOnStart` / `tempDir` 只存在于类型定义里，没有任何代码读取。核心媒体库只有在设置了顶层 `media.ttlHours` 时才清理。建议在 OpenClaw 配置里设置 `media.ttlHours`，例如 168（7 天）。
- **自建应用回调通道的上下游企业映射。** 每条入站同步写一次文件，但重启后从不读回，只影响上下游企业场景。本版未改。
- **思考内容合并的计算量随长度平方增长。** 实测 5 万字约 2 秒，属于次要问题，本版未改。
