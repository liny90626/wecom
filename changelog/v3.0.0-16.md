# 3.0.0-16（2026-10-11，LinKy fork）

修一处现网偶发问题：回复气泡变成「已收到新消息，合并思考。✅」，之后再没有回复，而用户并没有连续发消息。

## 现象

升级以来出现过 3 次，两种表现：

1. 同时发图片和文字，只回了一句「已收到新消息，合并思考」，之后没有任何回复；
2. 只发了一条消息，agent 的回复突然变成「已收到新消息，合并思考」。

## 根因

企业微信自己会往同一个会话推事件帧：当天首次进入会话的 `enter_chat`、成员在后台改权限后的 `auth_change_event`。这些帧和用户消息共用同一个会话（peer），插件把它们当作一条新消息派发：

- 用户这一轮已经交给 OpenClaw 在跑时，事件帧会中止这一轮的 run 并接管会话；被接管的气泡收到的原因固定写成「合并」，于是显示「已收到新消息，合并思考」；
- 事件帧不是聊天内容，不会并入用户的消息，用户的问题就此丢弃；
- 事件帧自己那一轮是「欢迎语」回合，回复走 `replyWelcome`，企微只在事件后 5 秒内接受，agent 跑完早已超时，用户什么也看不到。

配置了静态 `welcomeText` 的账号不受影响（静态欢迎语不经过派发器）。

现网日志未保留这 3 次的现场，无法逐次对证触发帧；以上是按代码路径复现得到的：在一条正在运行的用户消息之后送入 `welcome` / `event` 帧，旧实现必然中止用户回合并发出「合并」通知（用例见下）。

## 修复

- **系统事件帧不再抢占用户回合。** 同一会话有用户消息正在准备或运行时，`welcome` / `event` 帧直接跳过（日志 `[wecom-b3] system-inbound-skipped`），用户回合照常完成。反方向不变：欢迎回合运行中来了用户消息，仍由用户消息接管。`auth_change_event` 清 MCP 缓存的副作用在适配层完成，不受跳过影响。
- **接管但没有合并时，不再说「合并」。** 卡片点选、群里另一位成员的消息接管一轮正在运行的回合时，旧回合的内容不会带进新回合，但通知仍写「合并思考」。现在这种情况显示「已收到新消息，本条未处理完，如仍需要请重新发送。」（原文案「本条尚未开始处理」只适用于还没开始的回合，一并改为对两种情况都成立的说法）。

改动只在 `src/runtime/dispatcher.ts`（跳过判断、接管前先告知「未合并」）与 `src/transport/bot-ws/reply.ts`（一条文案）。

## 举一反三

按同一思路复查了其余会接管会话的入口：

- 媒体与文字的 1 秒合并窗口、被接管消息的正文与附件并入后继消息：逻辑未发现缺口，既有用例覆盖先图后文、先文后图、已有可见输出三种顺序；
- 同一条消息重复送达：适配层在创建回复前已按去重表丢弃；
- 主动推送（cron、`message` 工具）只标记外部活动，不接管会话。

仍然存在、本版未改的一点：没有配置静态 `welcomeText` 时，`enter_chat` 会跑一轮 agent，其回复受企微 5 秒限制大概率发不出去。这是既有行为，不影响用户消息；要彻底避免可给账号配置 `welcomeText`。
