# v3.0.0-v1（2026-09-05，LinKy fork）

发布标签 `released/3.0.0-v1`。这是 fork 切到上游 v3.0.0 基线后的第一个版本，三件事：**基线换成腾讯官方插件 2026.8.17 的重建**、**同时运行在 OpenClaw 2026.7.1-2 与 2026.9.1**、**Bot WS 车道 4 项稳定性修复加 2 项小修**。修复全部先在网关模拟器里复现，再修，再用同一用例验证。

## 一、基线：上游 v3.0.0

上游 `YanHaidao/wecom` 的 `v3.0.0`（commit `133773f`）不是 2.7.260 的增量，而是以腾讯官方 `WecomTeam/wecom-openclaw-plugin` 2026.8.17（commit `3b1cbe3`）为主线的重建。本版直接采纳这棵树，在其上做 2026.7.1-2 兼容与本轮修复。官方仓库截至 2026-09-05 的 main 仍是 `3b1cbe3`，没有更新的官方提交；上游文档 `OFFICIAL_PLUGIN_MIGRATION.md`、`UPSTREAM_BASELINE.json` 随包发布。

2.7.260 的 Bot WS 车道（`src/transport`、`src/runtime`、`src/capability/bot`）不在这棵树里。随之消失、需要在真机上重新体验的行为：

| 2.7.260 | 3.0.0-v1 |
| --- | --- |
| 长任务心跳（8 分钟状态帧、90 秒工具沉默看门狗、死窗后每 20 秒推送正文） | 没有。流窗口约 6 分钟关闭后气泡冻结，答案在结束时分片主动推送 |
| 思考窗口、过程步骤气泡 | 只有 `<think></think>` 占位与正文 |
| 新消息接管旧回合 | 同一会话严格串行 |
| final/block 双形状字节去重 | 依赖 OpenClaw 核心过滤重复 final；插件直接累加 |
| 运行时上下文围栏（入站转义、preamble/reasoning 剥离） | 未移植，新基线没有会话钩子 |
| 默认放行 `~/Desktop ~/Documents ~/Downloads ~/Movies ~/Pictures` | 只放行 SDK 默认根 + stateDir + `channels.wecom.mediaLocalRoots` |
| B1/B2/B3 字面量门禁 | 删除；双线兼容改由 `npm run compat:check` 真跑 |

**升级前的运维动作**：agent 若把要发的文件写到 `~/Documents` 这类目录，在 `channels.wecom.mediaLocalRoots` 里补上，否则出站会得到「没有权限访问路径」提示。

保留：多账号、upstreamCorps、动态 Agent、模板卡片、`wecom-cli` 与 16 个 Skills、增强工具 `wecom_doc` / `wecom_calendar`、Agent 车道 2048 字节切分与 1100 ms 节奏。

## 二、同时运行在 OpenClaw 2026.7.1-2 与 2026.9.1

上游 v3.0.0 面向 `^2026.8.1`。本版把 devDependency 钉回 `2026.7.1-2`（生产版本），peer `>=2026.7.1-2`，并对照两条线的 dist 逐项核对了适配：

| 适配 | 两条线的事实 |
| --- | --- |
| `setupContract` 按 `defineChannelSetupContract` 是否存在决定，`setup` 适配器同时提供 | 7.1-2 没有该工厂；9.1 用 `setupContract ?? plugin.setup` |
| `registerSecurityAuditCollector` 在 `registerFull` 里可选调用 | 两条线的 plugin api 都有；7.1-2 没有 `registerCapabilities` |
| CLI 描述符的 `machineOutput` 用非字面量对象保留 | 9.1 识别 `--json` 为机器输出；7.1-2 的类型没有该字段 |
| 账号配置本地合并（omit accounts/defaultAccount，groups 浅合并） | 与两条线 `createAccountListHelpers` 的语义等价 |
| 账号快照不再带 `lifecycle` | 两条线的 `ChannelAccountSnapshot` 都没有该字段 |
| `readResponseWithLimit({ chunkTimeoutMs })` | 7.1-2 只有 `chunkTimeoutMs`，9.1 两者都有 |

`npm run compat:check 2026.7.1-2 2026.9.1` 在仓库外的工作区（`~/.cache/wecom-openclaw-compat/`）对两条线各跑一遍 typecheck 与全量测试，本版两条线均通过。8.x 上不再需要放行 `plugins.entries.wecom.hooks.allowConversationAccess`，新基线没有会话钩子。

## 三、Bot WS 车道修复（先复现，再修）

复现载体是新增的 `src/monitor.gateway-sim.test.ts`：用内存网关驱动 `monitorWeComProvider` 全链路，断言用户实际收到的帧与推送。修复前 6 条用例红 4 条。

### 3.1 长回答按全文写帧，超过企微 20480 字节上限

复现：4 段共 48 KB 的回答发出 5 帧超过 `stream.content` 的 20480 字节上限；窗口过期后又整段一条推送。企微会拒绝超限帧，答案丢失。

修法：一帧预算 `STREAM_FRAME_MAX_BYTES = 15360`（官方上限的 75%，2.7.x 现网值）。气泡冻结在首帧，首帧不变不重绘；余量在收尾时按 `ACTIVE_PUSH_CHUNK_CHARS = 3500` 分片主动推送，条间沿用 1100 ms 节奏。窗口已过期时全文按同一规则分片推送。

### 3.2 finish 帧 ACK 丢失后答案静默丢失

复现：finish 帧被 SDK 的 5 秒 ACK 超时拒绝，原逻辑抛错、重试一次再失败后只留下 `finish_after_failure_failed` 日志，没有任何兜底。

修法：finish 帧任何失败都改走分片主动推送。ACK 丢失时那一帧可能已经落地，但没有回执就没有送达证明，宁可有限重复也不丢答案。日志 `stage=finish_frame_failed fallback=active_send`，推送 `reason=finish_unacked`。

### 3.3 846605 未识别为流失效

复现：finish 帧被网关以 `846605 invalid req_id` 拒绝，原逻辑只认 846608，同样走到丢答案。

修法：846605 与 846608 都映射为 `StreamExpiredError`，errcode 保留在异常上；随后按 3.2 的路径推送。

### 3.4 `message` 工具发文件失败却返回成功

复现：`outbound.sendMedia` 的 Bot WS 分支在上传失败或文件超限时，给用户发一条提示后**返回成功**，模型据此告诉用户「文件已发送」。这是 2.7.260-26 上「说发了但没到」体验的一条现成路径。

修法：Bot WS、Agent HTTP 兜底、上下游三条失败路径都先通知用户，再向工具抛出带原因的错误。

### 3.5 白名单拒绝的提示误导重试

复现：本地文件不在允许目录内时提示「无法处理文件 …，请稍后再试」，而重试不可能成功。

修法：识别本地回退实现的 `not under an allowed directory`，给出 `mediaLocalRoots` 配置提示。

### 3.6 `wecom diagnose --json` 在 9.1 上丢失机器输出标记

Codex 为了通过 7.1-2 的类型检查删掉了 `machineOutput`。改为非字面量描述符保留，两条线都通过类型检查。

## 四、2.7.260-26「agent 说文件发了，实际没到」

读完 -25 到 -26 的全部媒体相关改动后，没有找到一条必然让文件静默消失的代码路径，离线未能复现。可能的解释与所需日志见 `SESSION_HANDOFF.md` 第 4 节。本版在新基线上堵住了两条会造成同一体验的路径（3.4、3.5）；真机若再出现，抓 `stage=media_failed`、`stage=media_batch_failed`、`[wecom][outbound] … kind=media` 日志行。

## 六、升级与真机验收

1. 备份当前 OpenClaw 配置与 `yanhaidao-wecom-2.7.260-26.tgz`。
2. 把新 tarball 复制到本地磁盘，`openclaw plugins install "npm-pack:<本地路径>"`，重启网关。
3. 按顺序验证：发文件两种方式各一次（`MEDIA:` 指令、`message` 工具）；超过 6000 汉字的长回答，气泡应只显示首帧、其余以推送到达；6 分钟以上的长任务，结束时答案应以推送到达；把文件放在白名单外目录，应看到 `mediaLocalRoots` 提示而不是「请稍后再试」。
4. 观察长任务体验是否可接受（第一节的差异）。不能接受时回滚到 2.7.260-26，并把心跳移植单独立项。
